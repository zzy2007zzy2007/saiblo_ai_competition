## 2. 🔴 严重偏离（5 项）

### 2.1 熵值异常低下 —— 从训练开始即处于收敛态

**偏离描述**：

| 时间点 | 实际 entropy | 期望 entropy | 偏离倍率 |
|------|:---:|:---:|:---:|
| Episode 20 | **0.242** | 1.5-2.5 | **低 6-10 倍** |
| Episode 100 | **0.303** | 0.8-1.8 | 低 2.6-6 倍 |
| Episode 380 | **0.290** | 0.8-1.8 | 低 2.8-6 倍 |
| Episode 760 | **0.297** | 0.8-1.8 | 低 2.7-6 倍 |

**熵值全程在 0.24-0.31 之间极窄波动，没有经历"从高到低"的收敛过程。** 这低于期望中"收敛期"的下限（0.3），更远低于"探索期"的期望（1.5-2.5）。

**严重性分析**：🔴 严重

- 熵值过低意味着策略网络几乎不做探索，从最初就锁定了某个确定性策略
- 这直接导致后续多个问题的根因：动作分布不演进、科技从不升级、超级武器几乎不使用
- 策略一旦收敛到局部最优（如"只建塔不做其他事"），PPO 很难自行跳出
- **但注意**：config 中 `entropy_hard_coef=20.0` 和 `entropy_min_ratio=0.25` 表明框架已尝试对抗熵坍缩，说明这可能是一个已知问题

**诊断可行性**：🟢 高

诊断路径清晰，需要排查熵从何处开始就已很低，以及为何 warmup 机制未能提升熵。

**诊断方法**：

1. **检查初始模型权重**：查看 episode 0 的模型权重分布（`weight_stats.jsonl` 第一条）——如果初始权重已偏向某些动作（如 NO_OP 的 logit 远高于其他），说明初始化有问题
2. **检查 warmup 生效情况**：config 中 `warmup.entropy_adaptive=true`、`entropy_target_ratio=0.15`、`ent_coef_max=2.0`。需要验证 warmup 期间 `entropy_coef` 是否确实被调高（对照 `training_metrics.json` 中的 `entropy_coef` 字段序列）
3. **检查 `hard_entropy_penalty` 的贡献**：该值在 16-18 之间，说明有熵惩罚在生效，但不足以将熵提升到期望水平
4. **对比不同 `entropy_hard_coef` 设置**：尝试 `entropy_hard_coef=50.0` 或 `100.0` 观察熵是否上升
5. **检查是否从 checkpoint 恢复**：此训练可能是从已有模型恢复而非从零开始（需检查 `training.log` 中的启动日志）

**缺少的日志/信息**：

- ❌ `training_start.log` 不存在（无法确认是否为全新训练还是恢复训练）
- ❌ 缺少 episode 0 之前的初始模型权重 snapshot
- ❌ warmup 阶段（ep 0-200）的 `entropy_coef` 变化序列不完整（JSONL 从 ep20 开始）

### 2.2 科技升级完全缺失 —— 陷入"保守策略陷阱"

**偏离描述**：

| 指标 | 实际值 | 期望值 |
|------|:---:|:---:|
| `type_tech_upgrade` 动作占比 | **0.0%**（全训练周期） | 0.5%-3% |
| `rw_tech_bonus` 奖励分量 | **0.0**（全训练周期） | 5-10% 的总奖励占比 |
| 单场对局中 gen_speed L0→L1 | **0 次**（latest battle 抽样） | 至少 1 次，时机在 60-100 回合 |
| 详细对战中含科技升级的比例 | **180/771 = 23%** | 应接近 100%（均衡局必升） |

agent 在整个 760 episode 的训练中**从未执行过科技升级动作**。这意味着蚂蚁的 generation_level 和 ant_level 始终为 0，击杀奖励始终为 6（最低档）。

**严重性分析**：🔴 严重

- 这是经济模型文档中描述的"保守策略陷阱"的典型表现：agent 学会了建塔防守，但从未学会升级科技来提升长期收入
- 科技升级（L0→L1 仅需 200 金币）是打破"重建循环"、解锁更高击杀奖励（6→10→14→18）的关键
- 不升级科技的后果：阶段 3-5 收入比最优路径低 **18-25%**（参见经济模型文档 §2.2）
- 不升科技 → 蚂蚁永远是 L0 → 击杀奖励恒为 6 → 金币增量有限 → 永远无力升级 → 恶性循环

**诊断可行性**：🟢 高

诊断方向明确，核心问题是：为何 agent 从不选择科技升级？

**诊断方法**：

1. **检查科技升级的 action mask**：确认 `UPGRADE_GENERATION_SPEED` 是否在 action space 中且未被错误 mask 掉（对照 `type_valid_tech_upgrade` 字段，确认该动作在有效动作列表中）
2. **检查科技升级的 reward 信号**：`rw_tech_bonus = 0.0` 说明 agent 从未执行该动作，需要确认 reward 设计中科技升级是否有正向奖励
3. **检查 logit 值**：`logit_tech_upgrade` 全程在 0.06-0.11 之间，远低于 `logit_build_tower`（0.08-0.13）和 `logit_upgrade_tower`（0.76-0.88）。logit 本身不低，但可能与其他动作比较时概率被压缩
4. **检查 prob 值**：`prob_tech_upgrade` 约 3.5-4.1，与 `prob_noop`（0.5-0.6）和 `prob_build_tower`（17-23）相比极低。需要确认 prob 到最终动作采样的映射是否正确
5. **检查是否需要显式奖励引导**：如果 agent 因熵过低而无法随机探索到科技升级，可能需要临时添加 `rw_tech_bonus` 的 shaping reward 来"示范"这个动作的价值

**缺少的日志/信息**：

- ❌ 缺少 `type_valid_tech_upgrade` 在 warmup 早期的值序列（用于确认该动作是否始终在合法动作空间中）
- ❌ 缺少详细的 action sampling 日志（prob → 采样 → 最终 action 的完整链路）

### 2.3 胜率无进步 —— 训练 760 episodes 后仍打不过历史快照

**偏离描述**：

| 对手（添加 episode） | 当前 agent 胜率 | 期望胜率 | 偏差 |
|------|:---:|:---:|:---:|
| opp_45fa2f2a（ep 40） | **47.1%**（40/85） | > 65% | 落后 18pp |
| opp_36b7b3e8（ep 240） | **43.2%**（35/81） | > 60% | 落后 17pp |
| opp_07020730（ep 400） | **41.4%**（24/58） | > 55% | 落后 14pp |
| opp_06b5ddb1（ep 360） | **44.2%**（23/52） | > 55% | 落后 11pp |
| opp_64df9ba2（ep 600） | **27.3%**（3/11） | > 50% | 落后 23pp |
| opp_ae9a2015（ep 320） | **46.4%**（26/56） | > 55% | 落后 9pp |

**当前 agent 对所有 6 个有足够样本的历史快照均处于劣势或五五开。** 综合胜率仅 50.9%，且没有随训练提升的趋势。

**严重性分析**：🔴 严重

- 这是训练不收敛的最直接证据。期望中 agent 应对历史快照有 > 55-65% 的胜率
- 当前 agent 甚至在 ep40 就加入的古老对手（opp_45fa2f2a）面前也只有 47% 胜率
- TrueSkill：当前 agent mu=28.92，池内最高 mu=32.30（opp_64df9ba2），差距 3.38（约 1.5 个 sigma）
- 说明 **760 episodes 的训练没有产生可测量的策略提升**

**诊断可行性**：🟡 中

需结合其他偏离点综合分析，根因可能是熵过低 + 动作空间探索不足。

**诊断方法**：

1. **绘制胜率时序曲线**：从 `per_episode_stats.jsonl` 中按滑动窗口绘制 win_rate 变化，确认是否存在"先升后降"或"始终无趋势"
2. **对比对手策略**：从详细对战日志中对比当前 agent 与获胜对手（如 opp_64df9ba2）的动作模式差异——对手做了什么 agent 没做的事？
3. **检查 payoff 矩阵的对手间对战**：当前 payoff.json 只有 agent-vs-opponent 记录，缺少 opponent-vs-opponent 的对战记录。需要确认 opp_64df9ba2 的高 mu 值是因为它真的很强还是因为样本不足（仅 11 局）
4. **关注"被驱逐的强对手"**：驱逐历史显示 opp_9dee4d25（mu=25.83, 70局）、opp_4b45f6bc（mu=27.67, 43局）等被驱逐。它们的 mu 不低却被驱逐，需要检查驱逐算法是否合理

**缺少的日志/信息**：

- ❌ 缺少 opponent-vs-opponent 的对战记录（用于构建完整的 payoff 矩阵）
- ❌ 缺少按 episode 滑动窗口的胜率曲线（需额外分析脚本）

### 2.4 超级武器几乎不使用 —— 放弃了高价值战略工具

**偏离描述**：

| 动作 | 实际占比（全760ep） | 期望占比（学习期） | 单局使用次数（实际） | 期望单局次数 |
|------|:---:|:---:|:---:|:---:|
| LIGHTNING_STORM | **0.0%** | 3-8% | 0 | 3-5 |
| EMP_BLASTER | **0.0%** | 1-3% | 0 | 1-3 |
| DEFLECTOR | **~0.02-0.06%** | 3-8% | 偶尔 1 次 | 3-5 |
| EMERGENCY_EVASION | **~0.02%** | 1-3% | 偶尔 1 次 | 2-4 |

详细对战抽样显示：在 771 场详细对战中，仅 155 场（20%）使用了任何超级武器，且绝大部分仅使用 1 次 Deflector。

**严重性分析**：🔴 严重

- 超级武器是游戏中与建塔、升级塔并列的三大核心支出类别，不使用等于放弃 30-60% 的策略空间
- EMP（135 金币）可以完全禁用敌方核心塔群 10 回合——这是扭转战局的最高价值工具
- Lightning Storm（90 金币）可以清蚂蚁群、伤塔——直接创造突破窗口
- 经济模型推演表明：每局应使用 5-7 次超级武器。当前使用次数接近 0
- agent 的"只用塔"策略本质上是在 3 条战线中的 2 条上完全放弃

**诊断可行性**：🟢 高

**诊断方法**：

1. **检查超级武器的 action mask**：确认这些动作是否在有效动作空间中（`type_valid_lightning_storm` 等字段在 warmup 早期为 0，后期逐渐出现非零值，说明需要冷却结束 + 金币足够才可用）
2. **检查超级武器的冷却和金币条件**：`type_valid_lightning_storm = 0.0` 在大多数 episode 中——这意味着要么冷却未结束，要么金币不足。需要对照回合级数据确认
3. **检查 logit 和 prob**：`logit_deflector` 约 1.15-1.28（在所有动作中最高！），但 `prob_deflector` 约 24-33。高 prob 却低采样率说明可能被其他动作的概率优势所掩盖
4. **分析金币使用模式**：agent 的金币是否总在 30 以下（`our_coins_lt_30 = 70-73%`），导致超级武器（60-135 金币）永远不可用？

**缺少的日志/信息**：

- ❌ 缺少按金币区间统计的动作分布（虽有 `our_coins_lt_30` 等字段，但未交叉分析"有多少金币时做了什么动作"）
- ❌ 缺少超级武器冷却状态的时序数据（在 round_details 中应有但未被聚合分析）

### 2.5 奖励无增长 —— 训练曲线完全平坦

**偏离描述**：

| 阶段 | avg_reward 实际 | 期望趋势 |
|------|:---:|------|
| Episode 20-100 | 2030 → 2508（微升） | 在 0 附近，缓慢起步 |
| Episode 100-400 | 2508 → 2443（**不升反降**） | 加速增长 |
| Episode 400-760 | 2443 → 2480（**完全平坦**） | 高位震荡 |

avg_reward 在 2000-2800 区间内无趋势波动，**没有经历期望中的阶段 (1)→(2)→(3) 过渡**。

**严重性分析**：🔴 严重

- 但需注意 nuance：avg_reward 起始值 2030 是因为每个 training episode 聚合了 20 场对局（`num_collected=20`），单场 reward ~100-180。不是 reward scale 有问题，而是**没有增长趋势**有问题。
- per-step reward_mean 约 0.5，合理。但全程无增长意味着策略没有在优化。

**诊断可行性**：🟡 中

奖励无增长是症状而非根因。根因是熵过低导致缺乏探索，策略卡在局部最优。

**诊断方法**：

1. **分解 reward 增长瓶颈**：绘制 `rw_hp_attack`、`rw_coin_gain`、`rw_tower_survival`、`rw_speed_bonus` 各自的时间序列，找出哪个分量限制了总奖励增长
2. **检查 reward 上限**：对局长度 246 回合，基础收入约 369 金币，这是否已经接近当前策略的 reward 天花板？
3. **对比优势局和劣势局的 reward 差异**：从 per_episode_stats 中按 win/loss 分组统计 reward 差异

**缺少的日志/信息**：

- ❌ 缺少按 win/loss 分组的 reward 分量分解
- ❌ 缺少 reward 分布的直方图（用于判断是否 reward 本身方差过大掩盖了趋势）

### 3.2 对手池周转过快 —— 新对手来不及被充分学习就被驱逐

**偏离描述**：

| 指标 | 实际 | 期望 |
|------|:---:|------|
| 对手添加频率 | 每 40 episode 一个 | 每 100-200 episode 一个 |
| 驱逐频率 | 每 ~60 episode 一个 | 仅在池满且新对手更强时驱逐 |
| 被驱逐对手的最小对局数 | **4 局**（opp_d19fe677） | > 8 局（min_games_threshold） |
| 池中样本 < 20 局的对手数 | **5/10** | 0-2 |

12 次驱逐中有 6 次被驱逐的对手游戏数 < 20，包括 opp_d19fe677（4局）、opp_44b297b5（5局）等。这些对手还没来得及被充分评估就被移除了。

**严重性分析**：🟡 中等

- 过快的对手轮换导致 agent 无法针对性地学习对抗特定策略
- 驱逐算法可能被保护分（protection=2.0）扭曲——低游戏数的对手得到保护分后分数虚高，挤占了更有价值的对手的位置
- 但对手池管理是训练基础设施问题，不直接影响 PPO 算法本身

**诊断可行性**：🟢 高

**诊断方法**：

1. **检查对手添加的触发条件**：当前 `opponent_update_interval=40`，每 40 episode 强制添加新对手（无论当前 agent 是否已经能稳定击败所有对手）。预期的做法是"仅在 win_rate 过高时才添加"
2. **检查驱逐算法中的保护分逻辑**：`eviction_history.jsonl` 中 opp_d19fe677 的 protection=2.0，使其从 mu=24.63 涨到 26.63，但仍被驱逐——说明保护分机制存在问题
3. **建议调整**：将 `opponent_update_interval` 提高到 100+，并改为条件触发（win_rate > 70% 才添加）

**缺少的日志/信息**：

- ✅ 驱逐日志完整（`eviction_history.jsonl`）
- ❌ 缺少"为何在此时添加对手"的决策日志（对手选择逻辑的触发条件不可见）

### 3.3 塔升级率过低 —— agent 重建造轻升级

**偏离描述**：

| 指标 | 实际 | 期望 |
|------|:---:|------|
| UPGRADE_TOWER 占比 | **0.7-1.0%** | 10-20% |
| 单局塔升级次数 | ~2-3 次（抽样） | 4-7 次 |
| 建塔次数 vs 升级次数比值 | ~15:1 | ~2:1 |

agent 明显倾向于新建塔（15金币起）而非升级现有塔（60金币 L1→L2），即使升级的性价比更高。

**严重性分析**：🟡 中等

- 经济模型明确指出：已有 3 座塔时，升级 L1→L2（60金币）性价比高于第 4 座新建塔（90金币）
- 但 agent 似乎永远在走"建更多 BASIC 塔"的路线，这是次优策略
- 不过在当前低级策略水平下，这是可以理解的——新建塔的 reward 反馈比升级塔更直接

**诊断可行性**：🟢 高

**诊断方法**：

1. **对比 BUILD_TOWER 和 UPGRADE_TOWER 的单位 reward**：从 `actrw_build_tower` 和 `actrw_upgrade_tower` 字段看，两者的单次 reward 相近（~0.3-0.6），但升级的 `actcnt` 少很多
2. **检查升级塔的 action mask 覆盖率**：`type_valid_upgrade_tower` 约 7-9%，说明只有 7-9% 的 step 中升级塔是合法的（因为需要已有塔 + 不在 EMP 下 + 钱够）。这个覆盖率天然低于建塔
3. **检查 reward 设计是否对升级有足够激励**

### 3.4 累计金币偏低 —— 但仍在可接受范围

**偏离描述**：

| 指标 | 实际 | 期望 |
|------|:---:|------|
| avg_our_cumulative_coins | **900-942** | 900-1100 |
| avg_enemy_cumulative_coins | **904-957** | 明显 ≤ 我方 |

实际值在期望范围的下沿，且敌方金币常高于我方——这说明 agent 并没有在经济上压制对手。

**严重性分析**：🟡 中等

- 900-942 与 MediumRuleAI 实测值 948 接近，符合"保守策略"的特征
- 低于最优模型 1054 约 10-15%，在可接受但不够理想的范围内
- 主要原因是：没有科技升级 → 蚂蚁等级低 → 击杀奖励低 + 无 PRODUCER 产蚁

**诊断可行性**：🟢 高 — 与"科技升级缺失"直接关联。

### 3.5 回合数过早稳定 —— 缺乏"短→长"的演进过程

**偏离描述**：

| Episode | avg_rounds | 期望 |
|:---:|:---:|------|
| 20 | **253** | 50-150（初期） |
| 100 | **243** | 100-200（学习中） |
| 760 | **241** | 240-320（收敛期） |

回合数从 ep20 就已经在 243-254 之间，完全没有经历"从短到长"的演进。

**严重性分析**：🟡 中等

- 这可能说明两件事：(1) 初始对手（baseline agents: BasicTowerAI/BasicRandomAI/MediumRuleAI）本身就会导致长对局；(2) agent 的策略从一开始就是"有效"的防御策略
- 但缺少短对局的早期阶段说明 agent 没有经历"从不会玩到会玩"的过程——这可能是因为初始权重已经倾向于有效的防御策略

**诊断可行性**：🟡 中

**诊断方法**：

1. **检查初始 baseline 对手的对局长度**：如果 BasicTowerAI vs MediumRuleAI 的初始对局就长达 250+ 回合，那这个现象是合理的（不是 agent 的问题，是 baseline 对手的特性）
2. **单独测试 agent vs RandomAI**：看看是否会出现短对局（如果是，说明 agent 确实会防守）

- 要么超时判负的 tiebreaker 规则（die_count → super_weapon_usage → ai_time）总能分出胜负
- **这不构成问题**，仅作为记录

## 5. 根因分析：问题之间的因果关系

┌─────────────────────────────────────────────────────────────────┐
│                    根因假设（需验证）                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │

│         ↓                                                       │

│           ↓                  ↓                  ↓               │

## 6. 诊断优先级与行动计划

| 优先级 | 诊断任务 | 预计工作量 | 关键产出 |
|:---:|------|:---:|------|
| **P0** | 确认熵从何时开始低、为何 warmup 未能提升熵 | 小（1-2h） | 确认初始模型权重 / warmup 日志 |
| **P0** | 确认科技升级和超级武器是否在合法动作空间内 | 小（<1h） | action mask 正确性验证 |
| **P1** | 提高 entropy_coef / entropy_hard_coef 进行消融实验 | 中（需重新训练） | 熵值是否能被有效提升 |
| **P1** | 分析单局级别的金币-动作时序，确认"有钱但不用"vs"永远没钱" | 中（2-4h） | 金币是否是超级武器/科技的限制因素 |
| **P2** | 调整对手池更新策略（降低频率、条件触发） | 小（改配置） | 减少无效对手轮换 |
| **P2** | 添加科技升级的 shaping reward 进行引导 | 中（改 reward + 重新训练） | agent 是否能学会科技升级 |
| **P3** | 补充 opponent-vs-opponent 对战记录 | 大（改代码） | 完整 payoff 矩阵 |
