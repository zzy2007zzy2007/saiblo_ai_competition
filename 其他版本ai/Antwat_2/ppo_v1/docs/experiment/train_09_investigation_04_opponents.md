# Train 09 调查 04：对手池管理问题根因分析

> 日期：2026-05-30
> 调查范围：异常清单 §3.2 对手池周转过快
> 数据来源：server9 / `20260530_120710` 训练日志

---

## 1. 调查结论摘要

**对手池周转过快的直接原因是 `opponent_update_interval=40`（每 40 episode 添加快照），深层根因是 agent 策略无实质进化，导致新添加快照高度相似、整体技能分层不明显，使得驱逐算法频繁触发。**

这不是一个独立问题，而是**策略停滞（Report 03）在 SelfPlay 基础设施层面的反映**。

## 3. 根因分层分析

### 3.1 直接原因：`opponent_update_interval = 40`

Config 中 `opponent_update_interval: 40`，意味着每 40 episodes 强制添加快照。在 760 episodes 中这产生了 19 个快照（ep0/40/80/.../760），而池容量仅 10 个，必然导致频繁驱逐。

**期望值**（train_expectation.md）：每 100-200 episodes 添加一个对手。当前频率是期望的 2.5-5 倍。

### 3.2 深层原因：agent 策略无实质进化 → 快照高度相似

从 Report 01-03 可知，agent 的策略从 ep40 后基本不变（仅 NO_OP + BUILD_TOWER + UPGRADE_TOWER 的微调）。这意味着：

- **ep40 的快照**（opp_45fa2f2a, mu=28.31）与 **ep760 的当前 agent**（mu=28.92）在策略上几乎无差异（mu 差仅 0.61）
- 每隔 40 episode 添加的快照本质上是"同一个策略的微小变体"
- 当池中有 10 个几乎相同的对手时，TrueSkill 很难有效区分——**技能信号的区分度不够**
- 技能区分不够 → TrueSkill sigma 保持高位（尤其是低游戏数的对手）→ 排名不稳定 → 驱逐逻辑"随机"剔除对手

### 3.3 保护分机制的局限性

驱逐历史显示 protection 分确实存在（范围 0-2.0），但其效果有限：

| 被驱逐者 | games | protection | mu → final | 被驱逐时池内最低 mu 对比 |
|------|:---:|:---:|------|------|
| opp_d19fe677 | 4 | 2.0 | 24.63 → 26.63 | 仍有对手 mu > 27 |
| opp_44b297b5 | 5 | 1.5 | 17.08 → 18.58 | mu 极低，保护分无法弥补 |
| opp_cabd6eb1 | 7 | 0.5 | 21.71 → 22.21 | 保护分不足以改变排名 |

**保护分的计算逻辑**（从 eviction 数据反推）：
- `victim_final_score = victim_mu + victim_protection`
- protection 值 0.5-2.0，与游戏次数呈反比
- 但即使 +2.0 的 protection（opp_d19fe677，仅 4 局），在有 10 个对手的池中仍可能被淘汰

**根因**：保护分是"缓冲"而非"阻止"——它给低游戏数的对手一个加分，但在策略高度同质化的池中（mu 集中在 25-30 之间），2.0 的保护分不足以改变驱逐决策。

### 3.4 对手轮换与策略学习的恶性循环

```
┌─────────────────────────────────────────────────────────────┐
│                  对手池管理的恶性循环                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  Agent 策略停滞（仅 NO_OP + BUILD_TOWER）                    │
│         ↓                                                   │
│  新快照与旧快照高度相似（mu 差 < 1）                          │
│         ↓                                                   │
│  每 40ep 强制添加快照 → 池迅速填满                            │
│         ↓                                                   │
│  TrueSkill 难以区分相似对手 → 驱逐"随机化"                    │
│         ↓                                                   │
│  低游戏数对手被驱逐（甚至 4-5 局的也被淘汰）                   │
│         ↓                                                   │
│  Agent 面对不断变化的对手池，无法针对特定策略学习               │
│         ↓                                                   │
│  Agent 维持"通用但有限"的策略 → 策略继续停滞 → 循环            │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**对手池问题不是独立的 bug**——它是策略停滞（Report 03）在 SelfPlay 层面的放大效应。如果 agent 策略在持续进化（如从"只会建塔"到"会升级科技"到"会使用超级武器"），快照之间会有本质差异，TrueSkill 排名会更稳定，驱逐决策也会更合理。

## 5. 建议

1. **P1 - 将 `opponent_update_interval` 提高到 100-200**：当前 40 的间隔对于 760 episodes 的训练来说过短。建议改为 `opponent_update_interval: 160`（或至少 100），使对手有足够的评估时间

2. **P1 - 改为条件触发而非固定间隔**：最佳实践是在 win_rate 对当前所有对手 > 65-70% 时才添加快照，而非每 N 个 episode 强制添加

3. **P2 - 增强保护分机制**：给游戏次数 < 20 的对手更强的保护（如 protection = max(5.0, (20 - games) × 0.5)），确保新对手有足够的评估窗口

4. **P2 - 增加池容量**：当前 `opponent_pool_size: 10`，在 2000 episodes 的长期训练中可能不足。考虑增大到 15-20

5. **注意**：以上建议只有在**先解决策略停滞问题**（Report 02/03）后才有效。如果 agent 策略仍然同质化，仅调整对手池参数只是延缓症状而非根治
