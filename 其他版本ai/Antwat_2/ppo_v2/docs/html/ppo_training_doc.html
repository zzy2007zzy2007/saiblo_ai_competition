一、PPO 算法原理总览

Proximal Policy Optimization (PPO) 是目前强化学习领域最广泛使用的策略梯度算法之一。其核心目标是在每一轮更新中在提升策略性能的同时，防止策略发生过于剧烈的变化——因为一次过大的策略更新往往会导致灾难性的性能崩塌。

1.1 策略梯度的问题

在策略梯度方法中，我们通过梯度上升最大化期望累积奖励 J(π) = E[Σ γt rt]。标准的策略梯度更新为：

∇J(θ) = E[∇log πθ(a|s) · A(s,a)]

其中 πθ 是参数为 θ 的策略网络，A(s,a) 是优势函数。这个公式的直观含义是：如果某个动作的优势为正，就增大它的概率；反之则减小。

但问题在于：策略梯度没有限制每次更新的步长。如果使用同一个数据批次进行多次梯度更新（这在 PPO 中是标准做法），旧策略 πθold 和新策略 πθ 可能在几次更新后差异极大，导致训练不稳定。

为什么不能直接限制参数更新的步长？

策略网络的参数空间和策略分布空间不是线性对应的——参数的小变化可能导致策略分布的剧烈变化，反之亦然。因此，PPO 不直接约束参数变化量，而是约束 策略分布的变化量。

1.2 PPO-Clip 核心思想

PPO 的解决方案是使用重要性采样比率 (importance sampling ratio) 来衡量新旧策略的差异程度：

rt(θ) = πθ(at|st) / πθold(at|st)

当 rt(θ) = 1 时，新旧策略在动作 at 上的概率完全相同。PPO-Clip 的优化目标为：

LCLIP(θ) = E[min(rt(θ) · At , clip(rt(θ), 1-ε, 1+ε) · At)]
符号含义
rt(θ)新旧策略在动作 at 上的概率比
At时刻 t 的优势估计，正值表示该动作优于平均
ε裁剪阈值（典型值 0.2），控制允许的策略变化幅度
clip(r, 1-ε, 1+ε)将比率限制在 [0.8, 1.2] 之间

裁剪机制的本质：当优势 At > 0 时（该动作好），我们想要增大其概率，但增大幅度被限制在 1+ε；当 At < 0 时（该动作差），我们想要减小其概率，但减小幅度被限制在 1-ε。这相当于给策略更新加了一个"安全带"——每次最多变化 ε 倍。

为什么用裁减法而不是 KL 散度约束？

TRPO (Trust Region Policy Optimization) 使用 KL 散度作为硬约束，但计算复杂且需要二阶优化。PPO-Clip 用一阶优化实现了相似的信任区域效果，实现简单、计算高效、对超参数更鲁棒。

1.3 Actor-Critic 架构

本项目采用 Actor-Critic 架构：

  • Actor（策略网络）：输出动作概率分布 π(a|s)，决定"做什么"
  • Critic（价值网络）：输出状态价值 V(s)，评估"当前状态有多好"

优势函数 A(s,a) = Q(s,a) - V(s) 衡量"这个动作相对于平均水平的优劣"。在实践中，我们用 TD 误差或 GAE 来估计优势，而不是直接计算 Q 值。

1.4 GAE 优势估计

Generalized Advantage Estimation (GAE) 是优势估计的利器，它在偏差与方差之间做平衡：

δt = rt + γV(st+1) - V(st)    (TD 误差)

AGAEt = Σl=0T-t-1 (γλ)l δt+l
符号含义
γ (gamma)折扣因子，控制远期的奖励对当前的影响程度
λ (gae_lambda)GAE 权衡参数，λ=0 等价于单步 TD，λ=1 等价于 Monte Carlo
δt单步 TD 误差——当前奖励 + 下一状态价值 - 当前状态价值

GAE 的直觉：如果 λ 接近 0，我们主要信任当前的价值估计（低方差，高偏差）；如果 λ 接近 1，我们更相信实际奖励的累积（高方差，低偏差）。实践中 λ=0.95 是常见选择。

二、本项目 PPO 算法细节

本项目在标准 PPO-Clip 的基础上做了一些工程化的调整和扩展。以下逐一说明每项设计的动机和效果。

2.1 双优化器设计

与许多实现共享一个优化器的做法不同，本项目为策略网络 (Actor) 和价值网络 (Critic) 使用独立的优化器：

self.optimizer = optim.Adam(policy_params, lr=lr)
self.value_optimizer = optim.Adam(value_params, lr=lr_vf)

为什么这样做？

  1. 不同的学习率需求：策略网络和价值网络的 loss landscape 不同。价值网络的 MSE loss 相对稳定，可以用较低学习率；策略网络的 policy gradient 更敏感，可能需要不同的学习率。
  2. 梯度裁剪独立：价值网络的梯度范数通常远大于策略网络（MSE loss 的梯度幅度与 reward scale 相关），分开裁剪可以设置不同的 max_grad_norm。
  3. 优化器状态独立：各自的 Adam 动量/方差累积不会相互干扰。

参数分组通过参数名前缀识别：

VALUE_PREFIXES = (
    "value_cnn.",  # 价值网络 CNN 层
    "value_mlp.",  # 价值网络 MLP 层
    "value_head.", # 价值输出头
    "value_proj.",
    "value_layer_norm.",
)

2.2 Returns / 优势归一化

在 PPO 更新中，returns 和价值网络的 MSE loss 尺度高度依赖奖励信号的幅度。如果奖励范围变化（例如某一局的对战特别激烈），value loss 可能突然爆炸。

本项目的处理方式：

# 在 _ppo_update() 中：
return_mean = returns.mean()
return_std = returns.std() + 1e-8
returns = (returns - return_mean) / return_std   # ← 归一化到 N(0,1)

# 在 _prepare_minibatch() 中：
adv_mean = mb_advantages.mean()
adv_std = mb_advantages.std() + 1e-8
mb_advantages_norm = (mb_advantages - adv_mean) / adv_std  # ← minibatch 内归一化

注意：returns 在批级别归一化，优势在 minibatch 级别归一化。这样做的好处是 value loss 始终在一个可控的尺度上，不同 episode 之间不会因为奖励幅度不同而导致 loss 剧烈波动。

2.3 辅助任务损失

除了策略损失和价值损失，本项目引入了辅助任务 (auxiliary tasks) 来帮助网络学习更丰富的状态表示：

辅助任务预测目标权重参数
己方塔伤害本回合对敌方防御塔造成的伤害aux_tower_coef
己方金币收入本回合获得的金币数量aux_gold_coef
敌方塔伤害敌方本回合对己方防御塔造成的伤害aux_enemy_tower_coef
敌方金币收入敌方本回合获得的金币数量aux_enemy_gold_coef

这些辅助标签从对局轨迹中离线计算（见 `compute_aux_labels_from_trajectory`），不参与在线推理。辅助任务的本质是多任务学习——通过预测这些与游戏进程高度相关的量，强迫网络中间层提取更丰富的特征。

辅助任务为什么有效？

游戏对抗的本质是资源（金币、塔 HP）的争夺。如果网络的中间特征能够预测金币收入和塔伤害，这些特征必然包含了关于游戏全局状态的有用信息，进而帮助策略网络做出更好的决策。

2.4 NaN 保护机制

神经网络训练中 NaN (Not a Number) 的出现是训练崩溃的前兆。本项目构建了一套三级 NaN 防御体系：

第一级：推理时 NaN 保护 (NeuralAgent._forward)

# 当 log_prob 或 value 出现 NaN 时，回退到 0
if has_nan:
    log_prob = torch.tensor(0.0, device=self._device)
    value = torch.tensor(0.0, device=self._device)

第二级：训练时 Tensor 清理 (clean_tensor)

# 在 loss 计算前替换 NaN/Inf
new_log_probs = clean_tensor(new_log_probs)
new_values   = clean_tensor(new_values)

def clean_tensor(tensor):
    return torch.nan_to_num(tensor, nan=0.0, posinf=1e4, neginf=-1e4)

第三级：NaN 恢复机制 (NanRecoveryHandler)

当检测到 loss 中出现 NaN 时，跳过当前 minibatch；如果连续 NaN 次数超过阈值，回滚到最近一次健康的检查点权重并停止训练。

# 每次 PPO update 成功后保存健康状态
self._nan_handler.save_good_state(
    policy_state=self.policy.state_dict(),
    optimizer_state=self.optimizer.state_dict(),
    value_optimizer_state=self.value_optimizer.state_dict(),
)

# NaN 恢复时回滚
policy.load_state_dict(self._last_good_policy_state)
optimizer.load_state_dict(self._last_good_optimizer_state)

2.5 学习率调度

学习率调度器 `LRScheduler` 支持三种策略：

  1. Warmup：在前 N 个 episode 将学习率从 0 线性增加到目标值，避免初期训练不稳定
  2. Cosine Decay：训练过程中按照余弦曲线从初始值衰减到 0，在训练后期进行精细调优
  3. Fixed：保持初始学习率不变
# Cosine decay 实现
if cfg.cosine_decay:
    progress = episode / max(total_episodes, 1)
    factor = (1.0 + math.cos(math.pi * progress)) / 2.0  # [0, π] 上的 cos，从 1 到 0
    lr = cfg.lr_base * factor
    lr_vf = cfg.lr_vf_base * factor

四、核心代码实现总览

本章走读主要代码路径一次，重在理解整体执行流程和各个模块如何配合。我们不深入每一行代码的细节——那些将留到第五章。本章的目标是建立"代码地图"。

4.1 训练入口：train.py

训练从 train.py 开始。它的核心逻辑是：

  1. 解析命令行参数和 YAML 配置文件（支持 CLI 覆盖）

  3. 创建 PPOTrainer（内部构建网络 + 优化器）
  4. 创建 SelfPlayTrainer（内部创建 NeuralAgent + EpisodeCollector）
  5. 调用 selfplay_trainer.train() 开始训练循环
# train.py — 核心创建逻辑
trainer = PPOTrainer(
    env_factory=env_factory,
    config=config,
    device=device,
    base_dir=str(path_config.get_run_dir(run_id)),
    callbacks=callbacks,
)
trainer.log_config_summary()

selfplay_trainer = SelfPlayTrainer(
    trainer=trainer,
    config=config,
    path_config=path_config,
    run_id=run_id,
)

callbacks.init_callback(trainer)
callbacks.on_training_start()
selfplay_trainer.train(

)

关键设计：SelfPlayTrainer 接收一个已构建好的 PPOTrainer 实例。这种"组合优于继承"的设计使 PPOTrainer 可以独立于训练框架被测试和复用。

4.2 训练主循环：SelfPlayTrainer.train()

在 selfplay.py 中，train() 方法是整个训练的核心循环（第 507-557 行）：

def train(self, num_episodes, env_factory, callbacks=None):
    while self._episode_count < num_episodes:
        self._episode_count += 1                          # 1. 计数器累加
        pending_info, reward, length, result = \
            self._run_single_episode(env_factory)          # 2. 一局对战 → EpisodeBatch
        self._flush_batch_to_update(                       # 3. 缓存够了就触发 PPO 更新
            pending_action_stats=[pending_info]
        )
        self._run_periodic_tasks()                         # 4. 对手更新/对战评估/保存

每次循环执行一个 episode。这里的关键是 _run_single_episode 收集数据后，_flush_batch_to_update 判断是否累积了足够的数据（达到 n_envs 局）来进行一次 PPO 更新。

4.3 数据收集：EpisodeCollector.collect()

EpisodeCollector 封装了单局对战的完整数据收集。其 collect() 方法执行以下流程：

def collect(self, env, opponent_agent, opponent_id, self_first):
    batch = EpisodeBatch()
    observations, _ = env.reset()
    obs_self, obs_opponent = self._setup_observations(observations)

    while not done:
        # 1. 己方动作：通过 NeuralAgent 获取 (action, log_prob, value)
        action_self, log_prob, value = self._self_agent.act_record(obs_self)

        # 2. 对手动作：通过 opponent_agent.act() 获取
        action_opponent = opponent_agent.act(obs_opponent)

        # 3. 环境 step：同时执行双方动作
        obs_new, (reward, _), terminated, truncated, info = \
            env.step(action_self, action_opponent, self_first)
        done = terminated or truncated

        # 4. 写入 batch
        batch.add_step(obs_self, action_self, reward, value, log_prob, done)

        # 5. 更新观测
        obs_self, obs_opponent = self._update_observations(obs_new, ...)

    # 6. 附加辅助标签
    self._attach_aux_labels(batch, step_snapshots)
    return batch, battle_details

注意：每步同时收集 value（Critic 输出）和 log_prob（Actor 输出的对数概率）。这两个量在后续的 PPO 更新中是计算损失函数所必需的。

4.4 PPO 更新入口：_flush_batch_to_update()

SelfPlayTrainer._flush_batch_to_update()（第 440-504 行）是数据收集和模型训练的桥梁：

  1. 判断条件：batch_pool 中的局数达到 n_envs 且总样本数达到 batch_size
  2. 合并数据：EpisodeBatch.merge() 将多局数据拼接
  3. 质量检查：检测 NaN/Inf/全零奖励等异常
  4. PPO 更新：调用 trainer.ppo_update(merged)
  5. 记录指标：将训练 metrics 写入日志和监控系统
  6. 清空缓存：重置 batch_pool，准备下一轮收集
def _flush_batch_to_update(self, pending_action_stats=None):
    # 检查是否达到更新条件
    if len(self._batch_pool) < n_envs or total_steps < batch_size:
        return

    merged = EpisodeBatch.merge(self._batch_pool)

    # 质量检查
    is_valid, issues = self._trainer.check_batch_quality(merged)

    # PPO 更新
    metrics = self._trainer.ppo_update(merged)  # ← 核心调用

为什么合并后才更新？PPO 是一个 on-policy 算法——训练数据必须是用当前策略收集的。每一局对战使用同一个策略（self_agent 的 policy 引用），所以多局数据可以合并使用。合并更大的 batch 能降低梯度估计的方差。

5.2 GAE 实现：compute_gae()

compute_gae() 的代码只有 15 行，但理解了它就读懂了 PPO 中"数据如何转化为学习信号"的关键环节：

def compute_gae(rewards, values, dones, gamma, gae_lambda, device):
    # 1. 转换为 Tensor
    rewards_t = torch.tensor(rewards, ...)
    values_t  = torch.tensor(values, ...)
    dones_t   = torch.tensor(dones, ...)

    T = len(rewards)
    advantages = torch.zeros(T, device=device)
    gae = 0.0

    # 2. 逆向遍历（从最后一个时间步往前）
    for t in reversed(range(T)):
        # 如果 t 是最后一步，下一状态价值为 0（游戏结束）
        next_value = 0.0 if t == T - 1 \
            else values_t[t+1] * (1.0 - dones_t[t])

        # 3. 单步 TD 误差
        delta = rewards_t[t] + gamma * next_value - values_t[t]

        # 4. GAE 递推公式
        gae = delta + gamma * gae_lambda * (1.0 - dones_t[t]) * gae
        advantages[t] = gae

    # 5. returns = advantages + values（Critic 优化的目标）
    returns = advantages + values_t
    return advantages, returns

为什么逆向遍历？

GAE 的定义 At = δt + (γλ)δt+1 + (γλ)2δt+2 + ... 是一个累积和。从后往前遍历可以复用上一步计算的 gae——这正是递推公式 gaet = δt + γλ · gaet+1 的含义。

dones 的作用

当 dones[t] = True（游戏提前终止）时，(1.0 - dones_t[t]) = 0，GAE 递推被截断——gaet = deltat。这防止了跨越 episode 边界的价值传播，符合马尔可夫性质。

GAE 计算完后，PPOTrainer._compute_gae 还做了额外的数值裁剪：

advantages = torch.clamp(advantages, -1e4, 1e4)
returns    = torch.clamp(returns,    -1e6,  1e6)

这是为了防止极端的奖励值导致梯度爆炸。

5.3 _ppo_update()：顶层调度

_ppo_update()（第 108-151 行）是 PPO 更新的顶层调度函数。它执行三个主要步骤：

def _ppo_update(self, batch):
    ppo_cfg = self.config.get("ppo", {})

    # Step 1: 数据准备 + GAE
    tensors = batch.to_tensors(self.device)
    advantages, returns = self._compute_gae(
        tensors["rewards"].tolist(),
        tensors["values"].tolist(),
        tensors["dones"].tolist(),
    )
    td_errors = returns - tensors["values"]

    # Step 2: returns 归一化（防 value loss 爆炸）
    return_mean = returns.mean()
    return_std  = returns.std() + 1e-8
    returns = (returns - return_mean) / return_std

    # Step 3: 统计信息计算 + PPO 多轮迭代
    reward_stats = self._compute_reward_stats(tensors)
    type_metrics = self._compute_type_metrics(tensors)
    metrics = self._train_ppo_epochs(tensors, advantages, returns, ppo_cfg)

    # Step 4: 保存健康状态（用于 NaN 恢复）
    self._nan_handler.save_good_state(...)

    # Step 5: 聚合指标并返回
    result = self._aggregate_metrics(metrics, reward_stats, type_metrics, ...)
    return result

returns（价值网络拟合目标）		_train_ppo_epochs 中的每个 minibatch

5.4 _train_ppo_epochs()：多轮迭代

PPO 的一个重要特点是同一批数据可以重复使用多次（这就是需要裁剪的原因——防止同一批数据上多次更新导致策略偏离过远）。

def _train_ppo_epochs(self, tensors, advantages, returns, ppo_cfg):
    ppo_epochs = ppo_cfg.get("ppo_epochs")      # 4 或 10
    batch_size = ppo_cfg.get("batch_size")       # 512 或 1024
    target_kl  = ppo_cfg.get("target_kl")        # 0.02，早停阈值
    total_samples = len(tensors["rewards"])

    for epoch in range(ppo_epochs):
        indices = torch.randperm(total_samples, device=self.device)  # ← 每轮打乱
        for start in range(0, total_samples, batch_size):
            mb_indices = indices[start:start + batch_size]

            mb_data = self._prepare_minibatch(tensors, advantages, returns, mb_indices)
            step_metrics = self._process_minibatch(mb_data, ...)

            if step_metrics is None:  # NaN 导致跳过的 minibatch
                continue

        # KL 早停：如果策略偏离过大，停止后续 epoch
        if epoch_approx_kl > target_kl:
            break

打乱的重要性：每一轮 epoch 开始时 torch.randperm 重新打乱数据顺序，确保每个 epoch 看到的 minibatch 组成不同。这增加了训练的随机性，有助于泛化。

_prepare_minibatch 的功能是从完整数据中切出一个 minibatch 并做优势归一化：

mb_data = {
    "board":         tensors["board"][mb_indices],       # (M, 28, 19, 19)
    "global":        tensors["global"][mb_indices],      # (M, 33)
    "mask":          tensors["action_mask"][mb_indices], # (M, N)
    "actions":       tensors["actions"][mb_indices],     # (M,)
    "old_log_probs": tensors["log_probs"][mb_indices],   # (M,) 旧策略的对数概率
    "advantages_norm": mb_advantages_norm,             # (M,) 归一化优势
    "returns":       mb_returns,                       # (M,) 目标 returns
    "old_values":    tensors["values"][mb_indices],     # (M,) 旧价值估计
}
# M = minibatch 大小（通常是 batch_size，最后一批可能较小）

5.5 _process_minibatch()：前向 + 损失 + 反传

这是_process_minibatch() 的核心流程（第 327-398 行），它完成一个 minibatch 的完整前向-反向传播：

def _process_minibatch(self, mb_data, ppo_cfg, clip_eps, clip_eps_vf,
                      ent_coef, vf_coef, clip_values):
    # ── 1. 前向：用当前策略在新数据上评估 ──
    (new_log_probs, new_values, entropy, type_ent, target_ent,
     aux_preds, features) = self.policy.evaluate_actions(
        mb_data["board"], mb_data["global"],
        mb_data["mask"], mb_data["actions"]
    )

    # ── 2. 清理 NaN/Inf ──
    new_log_probs = clean_tensor(new_log_probs)
    new_values    = clean_tensor(new_values)

    # ── 3. 计算损失 ──
    loss_result = self._compute_losses(mb_data, new_log_probs, new_values, ...)
    if loss_result is None:
        return None   # NaN 检测到，跳过
    total_loss, aux_metrics, clip_fraction, ratio, log_ratio = loss_result

    # ── 4. 反向传播 + 梯度裁剪 ──
    skip_update, grad_metrics = self._backward_and_clip(total_loss, ...)
    if skip_update:
        return None   # 梯度异常，跳过

    # ── 5. 收集指标 ──
    return self._collect_step_metrics(mb_data, new_values, ..., clip_fraction, ...)

evaluate_actions 是网络的核心方法，它同时完成两件事：

  • 重新计算给定动作在新策略下的对数概率 new_log_probs（用于计算比率 rt(θ)）
  • 重新估计状态价值 new_values（用于计算 value loss）
  • 计算策略熵 entropy（用于熵正则化）

5.6 _compute_losses()：损失函数详解

_compute_losses()（第 400-464 行）是 PPO 算法的数学核心。让我们逐行解析：

比率计算

log_ratio = new_log_probs - mb_data["old_log_probs"]  # 对数域相减 = 除法
# 数值稳定裁剪：防止 log_ratio 过小或过大
log_ratio = torch.clamp(log_ratio,
    math.log(clip_values.get("ratio_min", 1e-5)),
    math.log(clip_values.get("ratio_max", 10.0)))
ratio = torch.exp(log_ratio)  # 重要性采样比率 r(θ)

ratio 的含义：如果 > 1，说明当前策略给出这个动作的概率比旧策略高；如果 < 1，说明概率降低了。ratio 是 PPO-Clip 的核心控制量。

策略损失 (Policy Loss)

surr1 = ratio * mb_data["advantages_norm"]               # 原始策略梯度目标
surr2 = torch.clamp(ratio, 1.0 - clip_eps, 1.0 + clip_eps) \
        * mb_data["advantages_norm"]                     # 裁剪后的目标
policy_loss = -torch.min(surr1, surr2).mean()               # 取最小值 + 负号 = 最大化
场景ratio优势min(surr1, surr2)效果
好动作，试图过度提高> 1.2+surr2 = clip(ratio)×A被裁剪器限制，停止过度提高
好动作，适度提高1.0~1.2+surr1 = ratio×A正常更新
差动作，试图过度降低< 0.8-surr2 = clip(ratio)×A被裁剪器限制，停止过度降低
差动作，适度降低0.8~1.0-surr1 = ratio×A正常更新

价值损失 (Value Loss) — 裁剪式 MSE

# 未裁剪的 value 预测
value_loss_unclipped = (new_values - mb_data["returns"]).pow(2)

# 裁剪后的 value 预测（限制每次变化幅度）
value_pred_clipped = mb_data["old_values"] + torch.clamp(
    new_values - mb_data["old_values"], -clip_eps_vf, clip_eps_vf)
value_loss_clipped = (value_pred_clipped - mb_data["returns"]).pow(2)

# 取二者最大值（最差情况下的 loss，鼓励保守更新）
value_loss = 0.5 * torch.max(value_loss_unclipped, value_loss_clipped).mean()

为什么 value loss 也要裁剪？策略裁剪防止策略分布突变，价值裁剪防止价值估计突变。二者原理相同——对价值网络来说，如果某一步 old_value 是 5，新估计变成 100，即使这个"更准确"，也可能导致训练不稳定。裁剪让价值估计也逐步变化。

熵损失 (Entropy Loss) — 鼓励探索

entropy_loss = -ent_coef * entropy.mean()

策略熵衡量策略的随机程度。最大化熵意味着鼓励策略保持探索，防止过早收敛到确定性策略。ent_coef 控制探索的权重——太小则策略过早确定化，太大则策略过于随机。

总损失

total_loss = policy_loss + vf_coef * value_loss + entropy_loss
# 可选：添加辅助任务损失
total_loss = self._add_auxiliary_loss(total_loss, mb_data, aux_preds, ...)

训练过程的最终结果：每个 PPO update 周期中，整个 minibatch 循环运行多次，每次计算 total_loss → backward → optimizer.step → 梯度裁剪 → 收集指标。训练结束后self._nan_handler.save_good_state() 保存当前的参数状态作为新的"健康检查点"。

5.7 梯度裁剪与安全检测

_backward_and_clip() 和 _check_and_clip_gradients() 组成了梯度安全层：

def _backward_and_clip(self, total_loss, max_grad_norm, max_grad_norm_vf):
    self.optimizer.zero_grad()          # 清零梯度
    self.value_optimizer.zero_grad()
    total_loss.backward()                # 反向传播

    skip, grad_metrics = self._check_and_clip_gradients(
        max_grad_norm, max_grad_norm_vf)
    if skip: return True, grad_metrics   # 检测到 NaN/Inf 梯度

    self.optimizer.step()                # 更新策略网络参数
    self.value_optimizer.step()          # 更新价值网络参数
    return False, grad_metrics

_check_and_clip_gradients 遍历所有参数：

  1. 检查每个参数的梯度是否包含 NaN/Inf → 如果发现，跳过整个 minibatch
  2. 计算策略网络和价值网络各自的梯度范数（用于日志和异常检测）
  3. 分别对策略参数和价值参数应用梯度裁剪（不同的 max_grad_norm 阈值）
# 梯度裁剪：策略网络梯度限制在 max_grad_norm，价值网络限制在 max_grad_norm_vf
nn.utils.clip_grad_norm_(policy_params, max_grad_norm)
nn.utils.clip_grad_norm_(value_params, max_grad_norm_vf)

梯度裁剪的作用：即使某个 minibatch 产生异常大的梯度，裁剪器也能将其"压回"安全范围，防止一步更新就破坏网络参数。这本质上是信任区域的另一种形式。

六、数据收集与 EpisodeBatch

本章重点介绍数据从环境产生到最终进入训练器的完整生命周期。

6.1 EpisodeBatch 数据结构

EpisodeBatch（定义在 batch.py）存储一局对战中每个时间步的完整快照。它的关键设计点是：

  • 纯数据容器：只是 list 的集合，不含任何训练逻辑
  • 独立于设备：数据以 numpy 格式存储，直到 to_tensors() 时才转移到 GPU
  • 可合并：merge() 静态方法将多局数据拼接为一个大 batch

to_tensors() 方法将数据转换为模型所需的张量格式——注意 actions 使用 dtype=torch.long（作为交叉熵损失的索引），其他字段使用 dtype=torch.float32。

6.2 EpisodeCollector 收集流程

EpisodeCollector 是对战循环的封装，其设计意图是：

  • 解耦：数据收集不依赖 PPOTrainer，只依赖 RecordingAgent 协议
  • 自包含：观测视角切换、奖励来源统计、快照采集都在内部完成
  • 可测试：传入 mock 的 RecordingAgent 即可测试收集逻辑

7.5 配置加载流程

配置加载路径经过三个层次，优先级由低到高：

  1. YAML 默认配置 — 从 configs/custom_antwar.yaml 读取，提供所有参数的默认值
  2. CLI 覆盖 — 命令行参数通过点号分隔的键路径覆盖（如 --ppo.lr 1e-4）
  3. 代码级合并 — ConfigParser 使用递归合并（deep_merge），深度合并嵌套字典，而不是简单替换最外层

最终的配置对象通过 AttrDict 提供属性访问（config.ppo.lr），兼具字典的灵活性和属性的便捷性。

八、辅助系统简介

本章简要介绍训练架构中非核心但不可或缺的辅助模块，供需要时深入阅读对应源码。

8.1 NeuralAgent

NeuralAgent 是推理逻辑的统一封装，替代了旧版 PPOAgent。它持有 policy 对象的引用——这意味着 PPOTrainer.ppo_update() 更新后的权重立即在 NeuralAgent 的后续推理中生效，无需额外同步。

关键接口：

  • act(obs) → action_id：仅做决策，不返回训练数据
  • act_record(obs) → (action, log_prob, value)：决策 + 返回完整的训练数据
  • get_value(obs) → float：仅评估状态价值

所有方法共享同一个 _forward() 方法，保证 NaN 保护逻辑统一应用。

8.2 安全机制

safety.py 提供了四个核心安全工具：

函数/类职责
check_tensor_nan()检测 tensor 中是否包含 NaN/Inf 值，返回布尔值
clean_tensor()用 torch.nan_to_num 替换 NaN/Inf 为安全值
reset_parameters()重置网络参数（用于回滚后重新初始化）
NanRecoveryHandler记录健康参数快照，NaN 连续超过阈值时自动回滚并停止训练

8.3 回调系统

回调系统基于 PPOCallback 抽象基类，支持以下钩子：

  • on_training_start() — 开始训练前触发
  • on_ppo_update_end(metrics) — 每次 PPO 更新后触发
  • on_episode_end(episode_count, reward, length) — 每局对战后触发
  • on_checkpoint(saved_path) — 保存检查点后触发

内置回调包括 CheckpointCallback（定期保存权重）和 TensorBoardCallback（记录训练曲线）。

8.4 对战评估

BaselineBattleCoordinator 负责定期评估当前策略的战斗力：

  • 创建 NeuralAgent 和 PPOWarAgent 的实例
  • 与多个基线对手（规则 Agent、历史策略快照等）对战
  • 统计胜率、平均奖励、对局长度等指标
  • 将结果写入日志供 TensorBoard 可视化

评估结果用于判断策略是否在持续提升，也是对手池更新策略（如淘汰最弱对手）的重要依据。
