Baseline Battle 模块详解

PPO v2 训练中的对战评估子系统 — 从类设计到跨进程执行

一、模块概览与文件结构

Baseline Battle 是训练流程中定期触发的一个评估子系统。它的职责只有一个：让当前正在训练的 PPO 策略与预设的基线 AI（规则策略）对战若干局，然后统计胜率。结果用于跟踪训练进度、检测策略退化、辅助判断是否应该保存 checkpoint。

1.1 外部调用链

整个模块的触发路径是一条清晰的调用链：

# train.py 启动时传入 battle 相关配置
train.py
   → SelfPlayTrainer.__init__(config)          # 存储 battle_interval 等参数
      → SelfPlayTrainer._run_periodic_tasks()   # 每个 episode 后判断是否该评估
         → _run_battle_evaluation()             # 创建 PPOWarAgent + BattleCoordinator
            → BattleCoordinator.run_ppo_evaluation_with_agent()
               → AgentLoader.load(baseline_name)
               → BattleSimulator.run_battles()
               → aggregate_results()
               → BattleReporter.generate_report()
            → 结果写入 eval_battle_log.jsonl

二、类的继承体系与职责

Baseline Battle 模块中的类可以分成两大体系：Agent 继承线（谁在对战）和 协作者线（怎么执行对战）。

2.1 Agent 继承线

AntWarAgent  # 对战基类，定义 choose_operations(state) 接口
  │
  ├── BasicRandomAI   # 随机选择合法动作，最弱的基线
  │
  ├── BasicTowerAI    # 建塔 → 升级塔 → 科技升级，简单的规则策略
  │     └── MediumRuleAI  # 在 Tower 基础上增加超级武器逻辑
  │
  └── PPOWarAgent     # PPO 适配器，内部持有 NeuralAgent
        # 流程: ObservationEncoder → NeuralAgent.act() → action_id → Operation

OpponentAgent  # 组合而非继承，包装 NeuralAgent 用于训练中对手

2.2 协作者线

BattleCoordinator           # 顶层入口，编排全流程
  ├── uses BattleSimulator  # 执行具体对战（多进程或顺序）
  │     └── uses AgentLoader # 序列化/反序列化 Agent 供跨进程传递
  ├── uses AgentLoader      # 加载 baseline Agent 实例
  ├── uses aggregate_results # 汇总多局对战结果
  └── uses BattleReporter   # 生成可读报告字符串

2.3 职责边界

类负责不负责
BattleCoordinator调度编排、异常捕获、结果收集具体的对战执行
BattleSimulator多进程管理、单局对战、超时控制Agent 加载、结果统计
AgentLoaderAgent 查找、实例化、序列化对战逻辑
AntWarAgent 子类根据状态输出操作列表对战环境管理
注意：OpponentAgent 和 PPOWarAgent 虽然都涉及加载模型，但角色不同。前者用于训练循环中的对手（从历史 checkpoint 加载），后者用于评估时的 PPO 方（使用当前正在训练的策略）。

三、工作流程——从触发到出报告

本章完整走一遍 baseline battle 的执行流程。重点是理解「数据在每个环节如何变换形态」。

3.1 触发条件

在 SelfPlayTrainer 中，每次 episode 结束后都会调用 _run_periodic_tasks(episode)：

def _run_periodic_tasks(self, episode: int) -> None:
    if episode % self._battle_interval == 0:
        self._run_battle_evaluation()
    # ... 其他周期性任务（save, opponent update ...）

battle_interval 在配置中指定（默认 20），即每 N 个 episode 评估一次。

3.2 创建 PPOWarAgent

_run_battle_evaluation() 首先将当前 PPO 策略包装为对战可用的 PPOWarAgent：

# 当前策略
import copy
policy_for_eval = copy.deepcopy(self._trainer.policy)
policy_for_eval.eval()

# 包装为 PPOWarAgent
ppo_war_agent = PPOWarAgent(
    player_id=0,
    ppo_agent=NeuralAgent(policy_for_eval, ...),
    observation_encoder=...,
    action_mask_handler=...,
)

# 加载 baseline 列表
baseline_agents = self._config["selfplay"]["baseline_agents"]
# 例如: ["BasicTowerAI", "BasicRandomAI"]

3.3 进入 BattleCoordinator

接下来创建 V2BattleCoordinator 并调用它的核心方法：

results: Dict[str, Dict[str, Any]] = coordinator.run_ppo_evaluation_with_agent(
    ppo_agent=ppo_war_agent,
    baseline_agents=baseline_agents,   # list of str
)

在 run_ppo_evaluation_with_agent 内部，对每个 baseline 名称执行：

for baseline_name in baseline_agents:
    # ① 加载 baseline Agent
    baseline_agent = AgentLoader.load(baseline_name, player_id=1)

    # ② 执行多局对战
    battle_results: List[Dict] = self._simulator.run_battles(
        ppo_agent, baseline_agent, self._config.n_battles
    )

    # ③ 汇总统计
    stats = aggregate_results(battle_results)

    # ④ 生成报告并打印
    report = self._reporter.generate_report(stats, "PPO", baseline_name)
    print(report)

    # ⑤ 记录
    results[baseline_name] = stats

四、Agent 注册与动态加载机制

AgentLoader 是 battle 模块中容易被低估的组件。它的核心挑战是：如何同时支持内置 Agent 和第三方外部 Agent 的加载，并且保证加载过程不会造成 import 污染。

4.1 内置注册表

KNOWN_BUILTIN_AGENTS: Dict[str, type] = {
    "BasicRandomAI": BasicRandomAI,
    "BasicTowerAI": BasicTowerAI,
    "MediumRuleAI": MediumRuleAI,
}

load(name) 的逻辑：先查注册表，找到了直接实例化；找不到，尝试动态加载。

def load(name: str, player_id: int = 0) -> AntWarAgent:
    if name in KNOWN_BUILTIN_AGENTS:
        return KNOWN_BUILTIN_AGENTS[name](player_id)
    # 外部加载，见 4.2
    return load_external(name, player_id)

4.2 外部 Agent 动态加载

外部 Agent 放在 baselines/<name>/ai.py 目录下，load_external() 需要在运行时导入它。但动态导入有陷阱：

def load_external(name: str, player_id: int = 0) -> AntWarAgent:
    # ① 清除可能残留的模块缓存
    for mod in ["ai", "common", "SDK", "AI"]:
        sys.modules.pop(mod, None)

    cwd, path, modules = os.getcwd(), sys.path.copy(), sys.modules.copy()
    try:
        # ② 插入搜索路径
        ai_dir = os.path.join(baselines_path, name)
        sys.path.insert(0, ai_dir)
        sys.path.insert(0, parent_of_ant_game_sdk)
        os.chdir(ai_dir)

        # ③ 动态导入
        spec = importlib.util.spec_from_file_location("ai", os.path.join(ai_dir, "ai.py"))
        module = importlib.util.module_from_spec(spec)
        spec.loader.exec_module(module)

        # ④ 尝试多种入口发现
        if hasattr(module, "create_agent"):
            agent = module.create_agent(player_id=player_id)
        elif hasattr(module, "AI"):
            agent = module.AI(player_id=player_id)
        # ... 更多 fallback
    finally:
        # ⑤ 恢复现场
        sys.path, sys.modules = path, modules
        os.chdir(cwd)

4.3 为什么要这么麻烦？

三个设计考量：

  • 避免 import 污染：两个外部 Agent 可能各自依赖不同版本的 SDK，不清除缓存会导致版本冲突。用 try/finally 保证无论如何都恢复现场。
  • 入口兼容性：不同开发者习惯不同（函数 vs 类，有参 vs 无参），load_external 需要兼容多种入口约定。
  • 序列化依赖：cloudpickle 序列化 Agent 时，如果模块路径已发生变化，反序列化会失败。每次加载都是"干净的"。

4.4 序列化方法（供跨进程使用）

@staticmethod
def serialize(agent: AntWarAgent) -> bytes:
    return cloudpickle.dumps(agent)

@staticmethod
def deserialize(data: bytes) -> AntWarAgent:
    return cloudpickle.loads(data)
为什么用 cloudpickle 而不是 pickle？ pickle 需要类定义在 __main__ 模块中才能序列化，且对嵌套函数、lambda 支持不好。baseline Agent 是动态导入的，其类定义不在 __main__ 里，cloudpickle 可以处理这种情况。

五、跨进程对战执行

本章是 battle 模块最核心也是最容易出问题的部分。核心问题：为什么一定要用子进程？如何在进程间传递 Agent？出了错怎么兜底？

5.1 为什么必须用子进程？

如果直接在训练主进程中执行对战，会面临三个问题：

  1. CUDA 内存冲突：训练期间 GPU 已经被 batch 数据占满。在同一个进程中实例化第二个推理用的 policy、编码状态、执行推理，会显著增加显存压力，甚至 OOM。
  2. 主进程阻塞：一局对战可能持续数百回合（每回合涉及 SDK 的 resolve_turn），主进程被堵住意味着无法响应回调、无法打印日志。
  3. 状态泄露：如果对战过程中 SDK 修改了某个全局状态，可能污染训练环境。

子进程隔离的方案：子进程有独立的 Python 解释器、独立的内存空间、独立的 CUDA context。对战结束后子进程退出，所有资源自动释放。

5.2 多进程调度

def run_battles(self, agent1, agent2, num_episodes) -> List[Dict]:
    total_tasks = num_episodes * 2  # 每轮 2 局（先手 + 后手）
    tasks = [(i % 2) for i in range(total_tasks)]  # [0,1,0,1,...]

    try:
        return self._run_battles_parallel(agent1, agent2, tasks)
    except Exception as e:
        logger.warning(f"并行失败: {e}，降级为顺序执行")
        return self._run_battles_sequential(agent1, agent2, tasks)

5.3 并行执行细节

def _run_battles_parallel(self, agent1, agent2, tasks):
    # 序列化 agent（跨进程传递必须）
    agent1_bytes = AgentLoader.serialize(agent1)
    agent2_bytes = AgentLoader.serialize(agent2)

    # 使用 spawn 创建子进程
    with ProcessPoolExecutor(
        max_workers=_DEFAULT_MAX_WORKERS,  # = 12
        mp_context=multiprocessing.get_context("spawn"),
    ) as executor:

        futures = []
        for i, first_player in enumerate(tasks):
            future = executor.submit(
                run_single_battle_process,
                agent1_bytes, agent2_bytes,
                first_player, self._config.max_rounds,
            )
            futures.append(future)

        # 收集结果（带超时）
        results = []
        for future in as_completed(futures):
            try:
                result = future.result(timeout=_BATTLE_TIMEOUT_SECONDS)
                results.append(result)
            except TimeoutError:
                results.append({"result": "error", "error": "timeout"})

        return results

5.4 子进程入口函数

run_single_battle_process 是子进程的起点 — 它必须是一个 模块级函数（不能是类方法或闭包），否则 spawn 无法序列化：

def run_single_battle_process(
    agent1_bytes: bytes,
    agent2_bytes: bytes,
    first_player: int,
    max_rounds: int,
) -> Dict:
    # 子进程中反序列化
    agent1 = AgentLoader.deserialize(agent1_bytes)
    agent2 = AgentLoader.deserialize(agent2_bytes)
    # 执行单局对战
    return _execute_battle(agent1, agent2, first_player, max_rounds)

5.5 优雅降级

如果并行执行全部失败（例如 CUDA 环境不支持 spawn），run_battles 捕获异常后降级为顺序执行：

def _run_battles_sequential(self, agent1, agent2, tasks):
    results = []
    for first_player in tasks:
        result = _execute_battle(agent1, agent2, first_player, ...)
        results.append(result)
    return results
进程安全注意事项：
① spawn 不继承父进程的 torch.Tensor、CUDA context，子进程中必须重新 model.to(device) + torch.no_grad()。
② 被 spawn 调用的函数必须在模块顶层定义（不能在类内部或 if __name__ 块中）。
③ ProcessPoolExecutor 的 max_workers 不宜过大（默认 12），否则 GPU 显存竞争反而更慢。

六、单局对战模拟

_execute_battle() 是 battle 模块中最底层的函数，负责一局完整的对战模拟。它不关心谁是 PPO 谁是 baseline，只关心两个 AntWarAgent 实例谁输谁赢。

6.1 函数签名与返回值

def _execute_battle(
    agent1: AntWarAgent,
    agent2: AntWarAgent,
    first_player: int,   # 0 = agent1 先手, 1 = agent2 先手
    max_rounds: int,
) -> Dict[str, Any]:

返回值格式：

{
    "result": "agent1_win" | "agent2_win" | "draw" | "error",
    "first_player": 0 | 1,       # 0=agent1先手, 1=agent1后手
    "total_rounds": int,
    "final_hp": {
        "agent1_hp": int,        # 始终指向 agent1 的 HP
        "agent2_hp": int,        # 始终指向 agent2 的 HP
    },
    "duration": float,            # 耗时（秒）
    "error": str,                 # 仅 error 时有
}

6.2 主循环

def _execute_battle(...):
    start = time.perf_counter()
    try:
        # ① 创建环境
        backend = load_backend(prefer_native=False)  # 纯 Python 后端
        state = PythonBackendState()

        # ② 回合循环
        for round_idx in range(max_rounds):
            # ③ 获取双方操作
            ops_0 = _get_ops(agent1, state, 0) if first_player == 0 else _get_ops(agent2, state, 1)
            ops_1 = _get_ops(agent2, state, 1) if first_player == 0 else _get_ops(agent1, state, 0)

            # ④ 过滤非法操作
            ops_0 = _filter_valid_operations(ops_0, state, 0)
            ops_1 = _filter_valid_operations(ops_1, state, 1)

            # ⑤ 结算回合
            state = backend.resolve_turn(state, ops_0, ops_1)

            # ⑥ 检查终局
            hp_0 = state.get_player_state(0).health
            hp_1 = state.get_player_state(1).health
            if hp_0 <= 0 or hp_1 <= 0:
                break

        # ⑦ 判定胜负
        result = ...

6.3 _get_ops 的签名兼容

不同的 Agent 实现可能使用不同的方法签名。有的用 choose_operations(state, player)，有的用 choose_operations(state)。通过 inspect.signature 动态检测：

def _get_ops(agent, state, player_id) -> List:
    method = agent.choose_operations
    if len(inspect.signature(method).parameters) == 2:
        return method(state, player_id)     # signature: (state, player)
    else:
        return method(state)                 # signature: (state)

6.4 非法操作过滤

_filter_valid_operations 不是简单的"能执行就执行"——它需要双重校验：

def _filter_valid_operations(ops, state, player) -> List:
    valid = []
    for op in ops:
        # 第一层：SDK 提供的快速校验
        if not state.can_apply_operation(player, op):
            continue
        # 第二层：TowerType 预检（绕过 SDK 的限制）
        if is_upgrade_operation(op) and not _validate_upgrade_target(op, state, player):
            continue
        valid.append(op)
    return valid[:MAX_OPERATIONS_PER_TURN]  # 每回合最多 3 个操作

为什么需要 TowerType 预检？因为 SDK 的 can_apply_operation 在某些升级场景下会返回 True，但实际执行升级时 SDK 内部会因为 tower type 不匹配抛出 ValueError。预检通过检查 TOWER_UPGRADE_TREE 来提前拦截这些非法升级。

6.5 胜负判定

if hp_0 <= 0 and hp_1 <= 0:
    result = "draw"
elif hp_1 <= 0:
    result = "agent1_win"   # agent1 始终代表 PPO
elif hp_0 <= 0:
    result = "agent2_win"
else:
    result = "draw"          # 超时双方都存活，算平局

七、难点 / 细节专题

7.1 先手/后手的双局制

每一轮 n_battles 会产生 n_battles × 2 局对战，其中一半 agent1 先手、一半 agent1 后手。

为什么必须这样做？

先手有显著的天然优势（AI 对战中，先手可以更早建造防御设施、更早攻击）。如果不轮换先手，胜率统计会被先手偏差严重扭曲。

tasks = [(i % 2) for i in range(total_tasks)]
# n_battles=4 → tasks = [0,1, 0,1, 0,1, 0,1]
# 0 = agent1 先手, 1 = agent1 后手

注意：两次对战是完全独立的——各自创建新的 PythonBackendState，不是"同一局再打一次"，而是"重置后换先手再打一次"。

7.2 子进程中的 CUDA 问题

当 PPO 策略在 GPU 上时，序列化/反序列化 + 子进程会带来几个隐藏问题：

问题原因解决方案
反序列化后模型在 CPU 上cloudpickle 不保留 device 信息子进程中反序列化后手动 .to(device)
spawn 子进程不能继承 CUDA contextspawn 不 fork，不继承 GPU 状态子进程中重新 torch.cuda.set_device()
序列化 torch.Tensor 可能失败某些 CUDA tensor 不支持 pickle序列化前确保 tensor 在 CPU 上
子进程不释放显存子进程退出时 CUDA 资源可能滞留设置 torch.cuda.empty_cache() 或在 finally 块中清理

7.3 cloudpickle 与非主模块序列化

Python 标准 pickle 序列化类实例时，要求类定义在 __main__ 模块中，否则只序列化一个"引用"。反序列化时如果 __main__ 没有这个类，就会报错。

# pickle 对非 __main__ 模块的行为
import pickle
data = pickle.dumps(BasicTowerAI(0))
# AttributeError: Can't pickle local object 'BasicTowerAI...'

# cloudpickle 可以正确处理
import cloudpickle
data = cloudpickle.dumps(BasicTowerAI(0))  # ✅
agent = cloudpickle.loads(data)               # ✅

cloudpickle 通过"序列化源代码 + 在目标解释器中重建类定义"的方式绕过了这个限制。代价是序列化体积比 pickle 大（包含源代码字符串），但在 battle 场景下 Agent 类通常很小，不是问题。

7.4 非法操作的双重校验

为什么 _filter_valid_operations 需要两轮校验？

  1. can_apply_operation：SDK 提供的方法，检查操作在游戏规则上是否合法（资源够不够、目标格子是否在范围内等）。但它在某些边界情况下不报错，却会导致后续 resolve_turn 抛出 ValueError。
  2. TowerType 预检：升级操作除了需要满足 can_apply_operation，还需要检查 TOWER_UPGRADE_TREE 中当前塔类型是否可以升级到目标类型。如果不做这个预检，resolve_turn 会因为 TowerType 不匹配而崩溃。

双重校验确保：进入 resolve_turn 的每个操作都是 100% 安全的。这是 battle 模块经过多次"SDK 内部抛异常"的教训后累积的经验。

7.5 超时兜底

如果某个子进程卡住（死循环、SDK 内部 deadlock），主进程不能无限等待。

# 方案一：as_completed + timeout
result = future.result(timeout=_BATTLE_TIMEOUT_SECONDS)  # 300s

# 方案二：超时后强制关闭并取消
except TimeoutError:
    executor.shutdown(wait=False)    # 不等待子进程
    future.cancel()                    # 取消剩余任务

超时的对战被标记为 "error"，在汇总时被计入 error_battles 但不会影响胜率计算。
