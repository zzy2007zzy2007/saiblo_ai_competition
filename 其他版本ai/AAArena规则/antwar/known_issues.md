# antwar：官方 SDK 的经济结算与后端不一致（已确认，**不修**）

> **状态**：已确认、可复现、**刻意不修**。
> **影响**：所有 antwar 候选（包括 94 名人类选手）看到的金币与裁判算的金币会逐渐分歧。
> **证据来源**：本 GamePack 收录的 Saiblo 后端源码
> `backend/src/coin.cpp`
> 对比官方公开 SDK `games/antwar/public_sdk/antwar/gamestate.py`。

## 一句话

官方 SDK 的 `downgrade_tower_income()` 是在 `downgrade_tower()` **已经改动/移除了塔之后**
才被调用的，于是它按「改完后的塔」分档计算返还，三种情况全部算错；
**拆除等级 1 塔时塔已被移除，函数走到 `t is None` 分支返回 `-1`，等于倒扣 1 金**。

```python
# public_sdk/antwar/gamestate.py:275-276
self.downgrade_tower(op.arg0)                              # 先改塔（BASIC 会被 pop）
self.coin[player] += self.downgrade_tower_income(op.arg0)   # 再按改完后的塔算返还
```

## 逐case对照

真后端（`coin.cpp::income_tower_destroy(level)`，`level` 是**拆前**等级）：

```cpp
case 0: tower_building_price /= 2; coin += tower_building_price * 0.8; break;  // 拆等级1
case 1: coin += LEVEL1_PRICE * 0.8; break;   // 等级2→1，60*0.8 = 48
case 2: coin += LEVEL2_PRICE * 0.8; break;   // 等级3→2，200*0.8 = 160
```

| 操作 | 拆前 type | 拆后 type | SDK 实际返还 | 后端应返还 | 偏差 |
|---|---|---|---|---|---|
| 拆除等级1（`BASIC=0`） | 0 | 塔被 `pop` → `tower_of_id` 返回 None | **−1** | `12×2^(N−1)`（N=拆前塔数） | 拆前 3 塔时偏 **−49** |
| 等级2→1（如 `HEAVY=1`） | 1 | 0 | `int(15×2^k × 0.4)` | 48 | 视塔数而定 |
| 等级3→2（如 `HEAVY_PLUS=11`） | 11 | 1 | 落进 `>0` 分支 → **48** | **160** | **−112** |

官方文档（saiblo game id=22 §3 经济系统）原文对得上后端，不对得上 SDK：

> 降级、拆除防御塔会返还 80% 的建造花销，即等级3降级为等级2返还160金，
> 等级2降级为等级1返还48金，拆除等级1返还 $12\times 2^i$ 金，其中 $i$ 为**拆除之后**己方防御塔的数量。

## 实测复现

在一局真实对局（`v002_cross_mortar_evasion` vs rank10，P0 座次）上，用官方 SDK 从
`seed + 双方录像操作` 重放，与回放记录的 `round_state` 逐字段比对：

```
被判非法而丢弃的录像操作: 4 条（首个在 r150 P1: 12 6 2）
coins        第 149 回合  回放=[14, 104]  重建=[14, 55]    ← 病灶，差 49
ants_alive   第 166 回合  回放=9          重建=10
camps        第 197 回合  回放=[50, 50]   重建=[50, 49]
```

第 149 回合 P1 在持有 3 座塔时拆掉一座 BASIC：后端返还 `12×2²=48`，SDK 给 `−1`，
差值 **49** 与观测完全一致。r150 P1 的升级操作随后被我们判为非法，
正是因为重建出的金币比真实少了 49 —— 那是**后果**，不是原因。

## 为什么不修

选手池里 94 名有名次的 antwar 选手全部是在这个 SDK 下开发与提交的。
修掉它会改变竞赛条件：人类选手的策略是围绕（错误的）SDK 反馈调出来的，
换成正确经济后他们的行为不再是当年那个行为，HL 与人类的对比就不成立了。
我们的 vendor 策略是「官方 SDK 原样进容器，只改文件名」，这条必须守住。

## 对我们代码的影响

1. **策略层（候选）**：不做任何处理。候选与人类选手面对同一个 SDK，这是公平的。
   但**这条信息本身是公开可推导的**（对照官方文档即可发现），所以写进
   `replay_skill.md` 供 agent 参考是正当的——人类选手当年同样可以发现它。
2. **测量层（我们的探针）**：**不能**用官方 SDK 的 `simulate_next_round()` 做长程状态重建，
   否则误差逐回合累积。必须每回合从回放的 `round_state` 同步权威状态
   （回放由真后端写出，是唯一可信来源），只用 SDK 做**合法动作枚举**。
   这与 antwar2 用 `sync_public_round_state` 的做法一致。
3. **评测层**：不受影响。胜负与分数一律取自回放/后端，从不取自客户端模拟。

## 一个待查的连带问题

同一局在第 199 回合以候选 `IA`（非法操作）结束，agent 自己的复盘写的是
「金币 98，不足 100，仍提交了紧急疏散」。既然 SDK 的金币会与后端分歧，
那么**候选看到的 98 可能本就不等于后端的真实金币**。也就是说：
部分 IA 判负可能不是「策略没算钱」，而是「SDK 的账和裁判的账不一样」。
这会系统性地惩罚**用拆塔换钱**的策略族，需要单独量化。
