# 预注册（本 goal 第 5–7 轮）：**搜索到底加了多少？**（决定第 ④ 步 AZ 环有没有地基）

> 2026-10-19 写（**在跑之前**）。上位目标 `goal-2600a56a`（打冻结基线 `grafted_sdk_A.pt` 两段各 ≥80%，双方禁闪电）。
> 章程：`docs/task_ruleV4_90_charter.md`。锚点：基线对 example = **0.8016（固定段）/ 0.8047（随机段）**。

## 0. 为什么这个实验比"K 扫描"更关键

第 ④ 步是"**用更强搜索当老师，做 search→policy 自蒸馏**"。它的前提是**搜索确实比策略强**——
真实对局里有强证据（`K=1` 时 0.0938 vs `K=24` 的 0.6562 ⇒ 搜索+MC 扛了 ~+56pp），
但**子博弈里从未测过**：那里"类"由 MC 菜单（5 候选）+策略头决定，搜索只负责位置 ⇒ 搜索的边际可能小得多。
**如果搜索的边际 ≈ 0，那么自蒸馏无从下手**（蒸馏一个不存在的改进），整条 ④ 就应该早早放弃、转向 S2（价值网）/数据侧。

## 1. 臂

| 臂 | 配置 | 对手 | 局数 | 用途 |
|---|---|---|---|---|
| **SF-ex** | **`K=1 ITERS=1`**（配合 `SKIP1=1` ⇒ **搜索被跳过**，只剩"钉类 + 该类 argmax 格"）| **example** | 128（固定段）| **廉价诊断**：与基线的 0.8016 比 |
| **SF-base** | 同上 | **`base_pkg`（冻结基线）** | 128（固定段）| **goal 判据**（也是个潜在候选：更简单的 agent 若 ≥80% 打基线，那就是达标）|

- 其余一切与基线相同（同一个 `grafted_sdk_A.pt`、`pos-only + mc_quiet + MC_UPG/MC_TOPK`、双方禁闪电）。
- 成本：搜索被跳过后**单局快得多**（预计 SF-ex 的 128 局 ≈ 1–2 h；SF-base 受基线侧拖累 ≈ 5 h）。
- 冒烟守卫照旧（我方建塔 ≤0.5/局 ⇒ 判退化跳过；闪电必须 0）。

## 2. 判据（先写死）

- **诊断判据（SF-ex）**：与基线同段 `0.8016` 比。
  * `SF-ex ≥ 0.70` ⇒ **搜索在子博弈里几乎不加东西** ⇒ 第 ④ 步（自蒸馏）**没有地基**，本 goal 应转向 **S2 价值网 / 数据侧**（并如实记录）。
  * `0.35 ≤ SF-ex < 0.70` ⇒ 搜索有中等价值 ⇒ ④ 值得一试（但要先看 K 扫描能否把搜索做得更强）。
  * `SF-ex < 0.35` ⇒ 搜索是主力 ⇒ ④ 最有希望。
- **goal 判据（SF-base）**：**两段**（固定段 + 随机段）对基线 `p̂ ≥ 0.80` ⇒ 候选 ⇒ 机械门（`goal_gate_vs_baseline.py`）+ 独立验证。
  只过一段 ⇒ 按目标规则**如实记未达标**。
- 逐段报 CI 与执先/执后；刚压线必须写明"点估计达到阈值 ≠ 统计上证明 >阈值"。

## 3. 预测（事后对照）

- **SF-ex**：我押 **0.25–0.45**（子博弈里"类"由菜单+头定，搜索只管位置；但位置在那盘棋里确实重要——升级/建塔都落在格子上）。
- **SF-base**：我押 **0.35–0.55**（**大概率打不过基线**——因为搜索-无关 = 把基线的一部分能力直接砍掉；但由于基线本身也可能过度搜索，出现"更简单反而略强"并非不可能）。
- 若 SF-ex **≥0.70**（即搜索几乎无用）：这是我**最想早知道的负结果**——它会立刻把路线从"加算力（④）"改到"改目标/数据（⑤）"。
