> * `M6b`（菜单 = {HOLD, 闪电(可执行时), 由**价值网 action_map** 在类 0..16 里选出的最优经济类}）

> ⇒ **菜单里"哪些类"进候选，是本机制最强的旋钮**（一个类进出 = 20+pp），必须在**受控**方式下探索。

## 1. 先做"可观测性"（0 号，必须最先做）

**M6c-OBS（观测，不判分）**：用 `AZAI_MC_DUMP`（补丁 `code/my_ai/az_intent/patch_mc_dump.py`）记录
**每次 MC 的候选、各候选分数、所选类、金币/血量**，跑 **8 局**（seed 7..10 双向）。
**目的**：知道 MC 到底在选什么（例如"降级类 16 被选中多少次、它赢了多少分差"），
**再据数据设计菜单臂**，而不是猜。⚠️ 该 dump 是**只读观测**（不改任何决策）。

## 2. 菜单臂（按优先级，写死）

| 臂 | 菜单 | 假设 |
|---|---|---|
| **M6c-M4** | {HOLD, 闪电(可执行时), **类 16 显式单列**, 最优经济类(0..15)} | 若 16 值钱，显式给它一个位置应恢复/超过 0.6641 |
| **M6c-2E** | {HOLD, 闪电(可执行时), **两个**经济候选（建新塔 vs 升级）} | 多给一个经济选项是否更好 |

- 每臂**直接 128 局验收**（新纪律）；对照 = **M6b 的 0.6641**（同代码同配置、逐局复现已证）；
- **机制必报**：建塔 / 降级 / 闪电 / 出招回合 + `mc_taken/mc_fallback`（埋点已加）；
- **晋级**：`≥0.70` ⇒ 机械门；`>0.6641` ⇒ 记为改进并继续沿该方向；否则记"该菜单改动无益"。
- 成本：每臂 ≈ 90 min（8 并行）。

## 3. 判定与纪律

- 菜单设计属于**决策表示**、不是判决规则；每次改动都记档（本预注册 + 寄存器）；
- **不许**把 `rule_v4`/前两名的动作当目标（本机制只用"模拟结果"与**我们的**价值网先验）；
- 若 M6c-OBS 显示 MC 的分数差普遍 ≈0（分辨不出候选），则本方向的解释要改成"MC 主要在**避免坏候选**"。


## 4. 追加（2026-10-06 11:0x，**在跑这批之前**）：`M6c-ROOT`（MC 只在根节点）

**新发现（读代码 + OBS dump）**：`_expand(node)` 在 256 次搜索迭代里**对每个被访问的叶节点都会调用**
（`bundle_mcts.py` L739），所以现在 `mc_quiet` 的 MC **不只在根节点跑**：
OBS dump 实测 **6,249 次 / 8 局 ≈ 780 次/局**（而"每 5 回合一次"的预期只有 ~80 次/局），
而且**连对手节点也被 MC 仲裁**。这既是成本来源，也让搜索树内的类分布被系统性地改写。

**臂 M6c-ROOT**：`AZAI_MC_ROOTONLY=1` + 同 M6b 菜单 ⇒ **MC 只在根节点仲裁 1 次/搜索**，
树内交回原采样（与 A1 的树内行为一致）。判据同 §2（直接 128 局，对照 M6b 0.6641）；
**机制必报**：`mc_taken`（应 ≈ 每局决策数 ~400，而不是 ~780）、建塔/降级/闪电/回合数、每局用时。
