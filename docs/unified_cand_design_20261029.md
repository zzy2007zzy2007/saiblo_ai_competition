## 0. 一句话

把候选生成从「先钉一个类（`pinned=[_ccls]*3`）」改成「从 `action_map` 全图**跨类 × 位置**取 top-k」，评估器（flat rollout 强评估器）**完全不动**。

## 1. 为什么这是正解（已有证据，不是新研究）

| 事实 | 出处 |
|---|---|
| 现役把 48 束钉在一个类上 ⇒ 78% 回合钉成 HOLD、`n_cand==1` 占 82.3%、候选缺 HOLD(26.8%) 也缺升级 | `why_effective_candidates_collapse_20261028.md` |
| 补 HOLD + 注入亚军非HOLD动作 = 45.8%，配对 +29.2pp（p=0.039）⇒ **评估器够用，是候选生成不行** | `nonhold_inject_ab_20261029.md` |
| `unified_action_search.enumerate_by_channel`（约 L104-118）**已写对**：含 HOLD 通道 + 升级枚举；当年 0/42 是评估器被改坏，不是候选生成错 | `prior_candidate_fix_research_20261029.md` |

## 2. 候选生成算法（精确到能照着实现）

**输入**：
- `action_map`：(24, 19, 19) 位置网输出（通道语义见下）
- 当前局面（`GameStateFacade`）：我方塔、金币、已占格、可升级目标
- `policy_heads`：类 logits（可选，仅方案 C 用到）

**通道 → 目标 op 枚举规则**：

| 通道 | 产出 op | 枚举规则（据 `decoder.py` 精确语义）|
|---|---|---|
| 0–15 塔型 | 11 BUILD 或 12 UPGRADE | 该通道前 m 个**合法格**：空格 ⇒ **建 Basic**（任何塔通道在空地都建 Basic，`decoder.py:444-446`）；我方已占格 ⇒ **升级向 `CHANNEL_TO_TOWER_TYPE[class_id]`**（`decoder.py:451-456`）；敌方格 ⇒ 丢弃 |
| 16 降级 | 13 DOWNGRADE | 我方已建塔格 |
| 17 闪电 | 21 LIGHTNING | 通道 argmax（闪电合法性几乎与格无关）|
| 18–20 超级武器 | 22/23/24 | `CHANNEL_TO_SUPER_WEAPON[class_id]`（EMP/DEFLECTOR/EVASION）|
| 21 基地升级 | 31 UP_SPEED | `OperationType.UPGRADE_GENERATION_SPEED`（`decoder.py:370-371`）|
| 22 基地升级 | 32 UP_ANT | `OperationType.UPGRADE_GENERATED_ANT`（`decoder.py:372-373`）|
| **23 HOLD** | 空 bundle `()` | 恒含 1 条（或按分数阈值，见 §6 待拍板）|
| **升级**（由 0–15 通道已占格分支自然产出；另可显式枚举兜底）| 12 UPGRADE | 兜底：显式枚举「我方塔 × 该塔合法升级目标」，`arg0 = tower_id`（**不是坐标**）、`arg1 = target_type`，用 `TOWER_UPGRADE_TREE` + `upgrade_step`（`decoder.py:82-94`）+ `can_apply` 过滤 |

> 升级为什么"无独立通道"：`action_map` 没有 op12 通道，升级是"塔意图通道解码到已占格"的产物（研究结论 ③）。所以必须显式枚举，不能靠通道 argmax。

**top-k 选择（3 个方案，见 §6 待拍板）**：
- **方案 A｜全局分数 top-k**：所有枚举出的 bundle 按各自通道分数排序，取前 k。最简单，但可能被某个高分通道垄断（比如建塔占满 48）。
- **方案 B｜每类 top-m 再合并**：每类取前 m 个，合并后截断到 k。保证类多样性。
- **方案 C｜类分数分层配额 + 类内按分数**：用 `policy_heads` 给每类分配配额，类内按 `action_map` 分数。最接近原"bandit 精神"，但只做候选生成、不做探索。

**去重**：bundle 键 = 完整 `(op_type, arg0, arg1)` 元组（空 bundle 用 `()` 表示）。去重后若 < k，**不填充**（重复候选无意义且浪费 rollout）。

### 方案 D（推荐，= 用户原始想法：类 bandit + 位置游标）

> 这是用户当年"类-位置统一搜索"的原始设计，比 A/B/C 更完整；当年实现把它退化掉了，这里恢复。

**单动作版**：
- 维护：每类滚动分数 `Q[c]`（**初始全相等（均匀）；类网先验接口预留但暂不启用**——类网目前基本不可用，要用得先重训）；每类"已选动作游标" `cursor[c]`。
- 循环到候选数达标：
  1. 按 `Q[c]` 的分布随机选类 c（UCB1 或 softmax）；
  2. 选位置：`cursor[c]` 空 ⇒ 位置图 argmax；否则看该类最后一个动作在位置图里排第 k ⇒ 选第 k+1 名；
  3. 对 (c, pos) 做 rollout，回写 `Q[c]` 与 `cursor[c]`。

**多动作组版**：分数仍按每个动作类统计；**游标按"动作类的规范多重集"索引，而非有序三元组**——去掉 HOLD、把类排序，`(hold,build,lightning)` 与 `(build,hold,lightning)` 归一到 `(build,lightning)`（它们产出的 bundle 相同，不该拆成两个游标、让预算被重复计算分摊、评估变稀）。位置分数 = 各类位置图分数之积（或 log-sum，防 0）；各类独立采样。

**关键设计判断（已和用户对齐）**：
- 位置由**静态位置图（先验）**提议，类预算由**学到的 Q[c]**分配 ⇒ 避免"类×位置笛卡尔积"。
- **两阶段预算**：bandit 只用**一小部分预算**生成候选（≈选够 K 个），再把**大部分预算**交给现有 flat 强评估器正式评估。理由：Q[c] 本身是弱评估器（每次 1 次 rollout 的均值），不能让弱评估器重新主导选类——当年 0/42 就是这么输的。
- HOLD 当"类 23、单位置（空）"处理，自然参与类采样。

**Q[c] 利用项：用"软最大"而非均值**（用户指出，已对齐）：
- 选类关心的是"这个类里**有没有**好动作"，不是"平均价值"；均值会被多数烂位置拖低、过早放弃含神手的类。
- 采用 **玻尔兹曼加权平均（带温度 softmax 当权重）**：`Q[c] = Σᵢ wᵢ·xᵢ`，`wᵢ = exp(β·xᵢ)/Σⱼ exp(β·xⱼ)`。β→0≈均值、β→+∞≈最大值；权重恒正 ⇒ 对负数成立；β 是纯温度旋钮。
- **为何不用 LogSumExp/mellowmax**：`(1/β)log((1/n)Σexp(βx))` 带折扣 `log(n)/β`，且折扣**最大恰在"一个神手+一堆垃圾"**的情形（β=3、n=10 时 Q≈0.24 vs 真值 1.0），与我们"想突出神手"意图相反。玻尔兹曼加权无该 log(n) 项：同样 β=3 时 Q≈0.96，天然贴近最大值（调研结论：Q[c] 数学上就是 mellowmax，见 `docs/prior_art_unified_search_20261030.md`）。
- 起步 **β=3**，超参扫 [1, 3, 8]；两阶段预算下可偏乐观（bandit 只生成候选、不强求精确）。
- **探索项保持标准 UCB**：`+ c·√(log N / n)`（c 另扫，如 [1.0, 2.0]），与利用项解耦、分别调；**τ（头 1..2 的 Boltzmann 采样温度）固定 1.0，只调 c**，避免多旋钮互相冒充。
- **信用分配（多动作束）**：Q[c] 的语义是"含 c 的动作组最好有多好"（见下条语义漂移），故把束整体分**完整回写**给每个组成类、**不打折扣**。1/|束长| 折扣反而与"组最好"语义矛盾（它退化成"c 的平均边际贡献"）。代价是"搭车类"（只靠好搭档才高分）也会拿到高 Q，但软最大 + 每形状游标会让 bandit 自然重配高分类、找到好组合，属可接受；且 Q[c] 只影响探索分配、不影响最终 top-k（后者按阶段 1 rollout 分）。**不拆 N_seen/N_eff**（二阶问题，同类不同位置/不同类不同 N[c] 均不重复计，不值）。
- **语义漂移（用户指出，可接受）**：因多动作束回写，`Q[c]` 从"类内最好**单动作**有多好"漂移成"**含**该类的动作组最好有多好"。这个漂移对探索分配无害、甚至更贴切——"含 c 的最好的组有多好"恰好就是"下一步该不该再组合 c"的正确信号。

**rollout 缓存与两阶段复用**（用户提出，已对齐）：
- **缓存键 = 规范化后的 bundle**（`(op_type, arg0, arg1)` 元组序列，去掉 HOLD）。不同通道/不同类序列解码出**同一个 bundle** 时只 rollout 一次（例：多个塔通道在空地都解码成同一个 `BUILD_TOWER(x,y)` ⇒ 一次即可）。
- **缓存命中 ≠ 跳过**（用户澄清）：命中缓存时**复用缓存分数、计入该类 Q[c] 的利用项**（等于已经 rollout 过），并**游标推进一格**继续试下一个位置，直到解出没见过的新 bundle 或该类位置穷尽。等价于"一次性做完了好几次 rollout、把游标推进了好几格，但只花一次查表时间"；玻尔兹曼加权对重复同值同样不敏感 ⇒ 重复计分不会撑虚 Q[c]。
- **候选键 = 带重数的规范多重集**：去 HOLD、排序、**保留重复**。`[build] ≠ [build, build]`、`[build, lightning] == [lightning, build]`（实现曾误用"集合"把重数抹掉，导致 `[build,build]`/`[downgrade,downgrade]` 生成不出，属 bug，须修）。
- **游标 = 按多重集（带重数），每个 bundle 形状独立推进**（用户最终定夺）：按类共享游标会让"一个位置被某一个 bundle 形状用掉后，其他形状再也组合不到它"——例：`[build]` 先把 build 游标从 A 推到 C，则 `[build(A), lightning(B)]` 永远构造不出。按多重集则每个形状从 argmax 独立推进，可保证该组合被探索到。
- 说明：实现曾因"按多重集重启 ⇒ 塌成 7 条/426 次重复"而改"按类"；该塌缩到底由"多重集索引"导致、还是由经济限制（金币不足 → 大量类 fail `can_apply`）导致，**尚未验证**（列为实现后的验证项）。故先回到按多重集 + 缓存推进，验证后若塌缩仍由多重集导致，再另行决策。
- **两阶段共用 rollout 数据**：bandit 阶段（生成候选）已做的 rollout 结果，直接喂给 flat 强评估器阶段复用，只补足剩余采样数到目标 N，不重复算。⇒ 这降低"两阶段"的额外成本，让"先用 bandit 粗选、再强评估"几乎不亏预算。

### 两阶段 rollout 的具体方式（用户提出，已对齐）

- **阶段 1（bandit 生成候选）**：用**确定性 rollout（`idle`，双方都不出手）**。本游戏确定性 ⇒ 每条候选 1 次就够（重复采样结果逐位相同，纯浪费）。实测 idle 比随机化略差但便宜得多，作初筛足够。
- **阶段 2（正式评估）**：与现役 flat 完全一致（`random` + opponent-only + `decay(1.0,3.0)` + horizon16 + `share_prefix=1` + N=64）。不动。

- **候选选择（谁进阶段 2）**：
  - 简单版：按**阶段 1 确定性 rollout 分**取 top-k。
  - 加权版：`rollout_score + λ·位置网分`（位置网分需**通道内 z-score 归一化**，消除不同通道语义/量纲差异）。
  - 建议起步 **λ=0（纯 rollout 分）**：位置网头部弱（建塔 @1 ≈1.2×随机），且位置网**已通过游标参与"提议顺序"**，不必再参与"选择权重"。λ 留作后续超参，等位置网变强再扫。

- **无位置的类**：HOLD（类 23）、基地升级（类 21/22）没有释放位置 ⇒ 各自是**单位置类**（游标恒指向那一个动作），bandit 仍把它们当普通臂处理，无需特殊分支。

### shape_pin 模式（2026-11-02 补充：介于 pin 与 unified 之间）

> 触发开关：`AZAI_CAND_MODE=shape_pin`（默认 off，不影响现役 pin/unified）。
> 实现与读数：`docs/shape_pin_mode_20261102.md`。

**一句话定位**：阶段 1 照跑 unified 的 bandit + 位置游标，但 s1 只用来挑**动作类的有序序列**
（"先降级→再建塔"这类有顺序的多重集），锁定该序列后，**位置由位置网先验（游标顺序，
argmax→rank k+1）直接取前 k 个**，不再按 s1 给所有候选排序。

**与 pin / unified 的区别**（各一句）：
- **pin**：一个类（MC 仲裁钉住）+ 该类内位置采样 ⇒ 只搜一个类；
- **unified**：跨类 × 位置 bandit，最后按**阶段 1 idle rollout 分（s1）**对全部候选排序取 top-k ⇒ s1 同时决定"选组"和"选位置"；
- **shape_pin**：s1 只决定"选哪个动作类序列"，**位置由位置网先验（游标）决定** ⇒ 把"s1 选组"与"s1 选位置"两个角色拆开。

**动机**：unified 的负结果里有一条归因歧义——s1（确定性 idle rollout）本身是个弱评估器，
让它同时给"选组"和"选位置"排序，可能把"位置网本来就该负责的位置提议"压下去了。shape_pin
想隔离这一点：组（类序列）由 s1 拍板，位置交回位置网先验，看这样能不能在不换评估器的前提下
回收一部分 unified 的损失。

**阶段 2 参数与 BASE 逐字一致**：shape_pin 只改"阶段 1 结束后选哪些候选进阶段 2"，阶段 2 仍是
现役 flat rollout（rollouts=64 / horizon=16 / batch=32 / random+opponent+decay(1,3) /
rounds=49152 / seed=53 / share_prefix=1 / eval=net / k=48），由 shape_pin 侧 stderr 的
`[shape_pin] engine=flat ...` 行证明。

**实验结果**（16 局 vs pin+flat，seeds 100..107 × 2 座位）：**1W-15L，胜率 6.25%（Wilson [1.1%, 28.3%]）；
血差 Δhp = −18.5（配对 t95 [−27.1, −9.9]）** ⇒ shape_pin 显著劣于 pin。61.7% 决策 s1 第一名是 HOLD、
锁定序列最多是降级 ⇒ "s1 只选组"仍被弱评估器的 HOLD/降级偏好拖垮（详见 `docs/shape_pin_mode_20261102.md`）。

## 3. 与 flat 评估器的衔接

- 现役预算 `N_eff = FLAT_ROUNDS / (k × 16)`，k 变化会改变每候选采样数。
- 建议固定 `AZAI_K=48`，用 top-k 截断（不要动态扩 k）。
- `extra_bundles`（注入/安慰剂/升级补丁）与 unified 候选**合并后一起去重**，再送评估器。
- 耗时警示：候选数从 ~1 → 48 会让单决策 rollout 量上升。实测 `n_cand` 中位 14 ≈ 1.4 s/决策、48 ≈ 26–31 s/决策（`why_effective_candidates_collapse_20261028.md` §成本）。**这决定了必须谨慎设 k，且阶段 1 冒烟必须先读耗时分布。**

## 4. 细节的坑（用户特别担心，列全）

1. **升级 `arg0 = tower_id`，不是 (x,y)** —— 历史踩过（`probe_upgrade_op`）。
2. **升级目标合法性**：`TOWER_UPGRADE_TREE[type]` 里选 target，逐条 `can_apply`（金币、等级上限、占位）。
3. **HOLD 与空 bundle 等价**：若候选里已天然出现空 bundle，别重复加（否则去重 + 浪费）。
4. **非法候选**：`can_apply` 逐条过滤；严格模式下一条非法 = 判负，绝不能漏。
5. **耗时上限**：候选数上升会放大 p95（现役 p95 已 ~17 s）。需要一个「候选数上限 + 若超时降 k」的保护，或阶段 1 实测后调预算。
6. **与补丁开关共存**：`AZAI_PIN_K` / `AZAI_ALWAYS_HOLD` / `AZAI_MC_UPG` 在 unified 模式下应**忽略或禁用**（避免双重路径、互相污染）。设计上：unified 模式直接接管候选生成，这些开关不再生效，并打一行 warning。
7. **零影响**：默认 `pin` 模式时逐位不变。验证法：同 seed 同历史 `INJECT_VS_RU_B`，`RESULT` + 双方 op 序列逐字节相同。
8. **训练口径（开放）**：这个生成器不训练；若以后想训位置网，teacher 标签怎么来、按哪个口径，见 §6。
