# 发现：扁平 rollout 评估器 vs 树搜索（M6c-ROOT）

> 2026-10-21。代码：`code/my_ai/az_intent/flat_rollout_greedy.py`、`code/test_match/ab_search_modes.py`
> 对照口径：`M6cROOT_128`（`docs/experiment_log.md` 行 6332；该臂 = 对 rule_v4 **0.7344**，
> 行 11337 明确标为"M6c-ROOT 基线"）

## 0. 一句话结论

**把"树搜索"换成"根节点一次动作网 + 每个候选 N 次 h 回合真实引擎 rollout + 批量叶值网"，
在 100 局同种子镜像对局里以 86W-14L（86.0%，t≈7.2）击败 M6c-ROOT，且每决策更便宜。**

⚠️ 但**绝对强度尚未校验**（见 §5）：必须先确认 A1 臂复现 0.7344，否则相对结论不成立。

## 1. 机制差别只有"评估器"

| | M6c-ROOT（树） | flat（本实验） |
|---|---|---|
| 动作网前向次数 | **257 次/决策**（256 次展开 + 根） | **1 次/决策**（根） |
| 每决策网络时间 | **1.95 s**（占搜索 81.8%） | ~0.01 s |
| 候选来源 | `_expand` 的 k 个 bundle | **完全同一个** `_expand` |
| 类判定 | 根节点 MC 仲裁（`mc_quiet` + `mc_root_only`） | **同一个**（同在 `_expand` 内） |
| 候选评估 | 树 256 次迭代、depth 4、visit 计数 | **N 次 h 回合 rollout，叶值网取均值** |
| 值网 | 同一份 `posnet_A_k5_m32` | 同一份 |

⇒ 唯一变化就是"怎么给候选打分"。

## 2. 实现要点（踩过的坑）

1. **`_mc_root` 必须挂上**。MC 仲裁的门控是
   `_is_root = (self._mc_root is not None and node is self._mc_root)`，
   而 `_mc_root` 只在 `BundleMCTS.search` 里赋值。自定义 `search` 忘了设它 ⇒
   `MC_ROOTONLY=1` 时**仲裁被静默跳过**，实验直接作废。
2. **叶子只跑值网、且批量**。若复用 `net_fn`（三网）在叶子上，7.6 ms/次 × 600 叶 = 4.6 s，爆预算。
   ⇒ 单独 `load_three_models()[2]`，batch=32（CPU 实测最优：264 µs/条；batch 再大反而退化到 490 µs）。
3. **时间预算自调节**：`max_total_rounds`（默认 39,000 ≈ 2.45 s @62.7 µs/回合），
   候选多时自动压低每候选采样数 N ⇒ 每决策总回合数可控。
4. **单候选直接返回**（与 `skip_single_candidate` 一致）：部署口径下大量回合只有 1 个候选。

## 3. 结果（全部同 ckpt、同候选、只有评估器不同）

| 批次 | seeds | 局数 | flat 战绩 | 胜率 |
|---|---|---|---|---|
| pilot | 7–10 | 4 | 4W-0D-0L | 100% |
| 批次 2 | 11–42 | 32 | 28W-0D-4L | 87.5% |
| 批次 3 | 43–106 | 64 | 54W-0D-10L | 84.4% |
| **合计** | 7–106 | **100** | **86W-0D-14L** | **86.0%** |

SE(100 局) ≈ 5.0%，t ≈ 7.2。三批独立且一致（84–88%），不是单次侥幸。

## 4. 成本（同一局面，round 200，24 候选）

| | 耗时 | 分解 |
|---|---|---|
| M6c-ROOT（256 iters, depth 4） | **2.45 s** | 网络 1.95 s（81.8%）+ 其余 0.5 s |
| flat（N=8, h=32） | **1.01 s** | expand 0.10 s + rollout 0.91 s（6,144 回合） |
| flat（N=16, h=64，主配置） | ~2.0 s | 回合数 24,576 |

⇒ **更强且更便宜**，且便宜的部分正好是"网络时间"（81.8% → ~1%）。

## 5. 必须补的校验（未完成前不下最终结论）

1. **绝对强度**：A1 臂（mcts + every5）对 rule_v4 是否复现 **0.7344**？

   **已测（64 局，seeds 7–38 双向镜像）**：**42W-22L = 0.656**（判词全部来自官方 5 级级联，
   无僵局嫌疑，p0 38 胜 / p1 26 胜）。
   与 0.7344 差 **7.8pp**，而 64 局的 2SE ≈ 12.5pp ⇒ **不能判定偏离，但也未确认**；
   要把区间压到 ±5pp 需要 128 局。

   ⚠️ **逻辑澄清**：head-to-head 的 100 局里**两侧 env 完全相同**（只差 `AZAI_SEARCH`），
   所以"配置是否等于冠军口径"只影响**结论对外部的相关性**，不影响该对照的内部有效性。
   一个共享的、略弱的配置无法解释 86% 的败率差。

## 5b. 2026-10-21 下午补测结果

### (a) 四臂：`{mcts, flat} × {MC_EVERY=5, 1}`，各 64 局 vs rule_v4

| 臂 | 搜索 | MC_EVERY | 战绩 | 胜率 | 终局血量差均值 |
|---|---|---|---|---|---|
| A1 | mcts | 5 | 42-22 | 0.656 | +1.56 |
| A2 | mcts | 1 | 43-21 | 0.672 | +3.28 |
| A3 | flat | 5 | 57-7 | 0.891 | +12.02 |
| **A4** | flat | 1 | **63-1-0** | **1.000** | **+16.23** |

搜索方式的效应（+23.5pp）远大于 MC 覆盖度（+1.6 / +10.9pp）。

### (b) MC_HORIZON 扫描（flat + every5，各 64 局 vs rule_v4）

| MC_HORIZON | 战绩 | 胜率 |
|---|---|---|
| **256**（M6c 原配置）| 57-7 | **0.891** |
| 128 | 63-1 | **0.984** |
| 64 | 53-3（56 局）| 0.946 |
| 32 | 61-3 | 0.953 |

⇒ **H=256 是唯一离群点**；砍到 128 及以下即稳定在 0.95–0.98。
推测原因：安静 rollout 的方差随 h 增长，而仲裁每类只采样一次 ⇒ 长 h 把噪声喂进了类选择。

### (c) T1：MC 覆盖度的**内部对打**（flat/every1 vs flat/every5，64 局）

| 指标 | 结果 |
|---|---|
| 胜率 | **34W-0D-30L = 53.1%**（SE 6.25% ⇒ 不显著）|
| 血量差（A−B）| **+1.44**，95%CI **[−1.0, +3.8]** |
| 单局耗时 | every1 **3.6 min** vs every5 **4.3 min** ⇒ **全回合仲裁反而更快** |

⇒ **结论：`MC_EVERY=1` 没有真实增益**。A4 的 1.000 vs A3 的 0.891（+10.9pp）
是 rule_v4 的**天花板假象**；内部对打只剩 +3.1pp（不显著）。
建议维持 `MC_EVERY=5`（也不慢，更省）。

> 教训：**所有 vs rule_v4 的读数在 0.89 以上都要打折**，判别必须用内部对打。

### (e) **轴序 bug 与位置通道质量重测（2026-10-21 深夜）**

**Bug**：`make_position_masks` 与网络 `action_map` 的空间轴都是 **`[x][y]`**
（`decoder.decode` 里是 `x, y = np.unravel_index(argmax, ...)`），
但 `unified_action_search.py` 早期版本写成 `[ch, y, x]` ⇒ **全部转置**。
症状：33 个可建格里只枚举出 **4** 个建塔（应 31）。修正后 31 与引擎判定一致。
**该 bug 影响到的旧读数（已作废）**：
- "统一搜索在真实中局选中升级" —— 那是转置先验下的候选集；修正后该局面选的是建塔 `(11,4,9)`；
- "建塔通道与 adv 反相关（−0.247）" —— 见下，修正后是 +0.046。

**重测（18 个真实中局局面，`adv` = 打完不推进的 1-ply 值网差分）**：

| 通道 | top-1 与 1-ply 值网一致 | **位置图 vs adv 的 Spearman** | 判读 |
|---|---|---|---|
| 闪电(17) | 0% | **+0.738**（均值 +0.765，n=6）| **强信号** |
| 建塔(0) | 0% | **+0.046**（均值 +0.049，n=12）| **基本无信号** |

⇒ **除闪电外，位置图不能用于排序**（用户 2026-10-21 的判断成立）。

**对各实验解释的影响**：

| 实验 | 是否受影响 | 说明 |
|---|---|---|
| T2（cells4 > cells0，75%）| ⚠️ | `mc_cells` 用 `action_map` 取前 4 格，而经济类排序无信号 ⇒ 那 4 格≈随机。增益更可能来自**类比较的样本变多（边际更稳）**或**引入我方塔格（多表达升级/降级）**，不能解释为"选格更准" |
| flat 胜 mcts（86%）| ⚠️ 部分 | flat 候选来自 `_expand` 采样（依赖位置图）⇒ 经济类候选覆盖差；胜因更可能在评估器 |
| 统一搜索 | ✅ | 通道预算已改为**类网 softmax**；通道内排序虽用坏通道，但建塔格**全部枚举**（cap 不生效）⇒ 影响很小 |
| 仲裁评估器对照 | ✅ | 只换评估器 |

**重训优先级据此调整**：第一优先是**建塔通道**（不是"改进"而是"从零建立信号"），
目标用 `adv`（冻结值网的 1-ply 优势），覆盖 16 个塔意图通道。


### (f) **根因：`int('op')` 一行 bug 让「升级」从未被执行（2026-10-22）**

对亚军的 32 局里我们 **0 次升级**（对手 8.2%）。我先后归因为"值网不认可升级""需要重训"
"需要照抄亚军的硬编码奖励"——**全部是错的**。真正原因是 `bundle_mcts.py` 里的一行：

```python
_ccls = (int(_c[0]) if isinstance(_c, (tuple, list)) else int(_c))   # 先执行
if isinstance(_c, (tuple, list)) and _c[0] == "op":                  # 才判断
    self.mc_last_explicit = (...)
```

显式升级候选的形式是 `("op", 12, tower_id, target)`，`_c[0]` 是**字符串 "op"** ⇒
`int("op")` 抛 `ValueError` ⇒ 被宽 `except Exception` 吞掉 ⇒ 走 fallback（`pinned = 类头 argmax`）
⇒ **`mc_last_explicit` 永远是 None ⇒ 桥接永远拿不到升级 op ⇒ 升级动作自落地起一次都没被执行过**。

**修复后（30 个真实中局、双方都有塔的局面）**：

| 仲裁模式 | 升级被选中 | op 中位排名 |
|---|---|---|
| quiet256（现状，**不加 bonus**）| **12/30（40%）** | 2.0 |
| net32 | 5/30（17%）| 3.0 |
| quiet + bonus 0.05 / 0.10 / 0.20 | 47% / **63%** / 73% | 1.0 |

⇒ **升级通路本来是通的，只是执行环节被异常吞掉了**；bonus 只是把它推得更高，不是必需。
⇒ 之前"5000 局低质量数据里塔类型 0 占 99.7%"的观察仍成立（那些局由 M6c 裸策略生成），
但它**不是**当前 0% 升级率的原因。
⇒ 教训：**宽 `except` 会吞掉"选择成功但执行失败"这类错误**，表现为"某个动作类永远不出现"，
看起来像模型/数据问题，实际是一行 API 误用。
