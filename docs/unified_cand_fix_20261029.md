## 0. 一句话

按最新设计把游标/缓存口径对齐：**束内允许重复类**、**候选键 = 带重数的规范多重集**、
**游标按形状（= 多重集）索引、每形状独立推进**、**缓存命中 = 复用分数 + 计入 Q[c] + 推进游标**。
并用"富局 vs 穷局"回答了上一轮遗留的问题：**塌成个位数的真因是经济限制（金币买不起），不是多重集索引**。

## 1. 改了什么（只碰 `unified_cand.py` + `az_bridge_ai.py` 的 2 行日志）

| # | 位置 | 旧 | 新 |
|---|---|---|---|
| ① | `_pick_group`（原 `generate` 内联） | `exclude={x for x in picked if x != HOLD}` ⇒ 束内**非 HOLD 类不重复** | 允许重复：头 0 用 `_ucb_pick()`（argmax），头 1..2 用 **`softmax(UCB/τ)` 采样**（`AZAI_CAND_TAU` 默认 1.0）⇒ 能出 `[build,build]` |
| ② | `_pick_group` | `tuple(sorted({c for c in picked if c != HOLD}))`（**集合**，抹掉重数） | `tuple(sorted(c for c in picked if c != HOLD))`（**保留重数**的规范多重集）⇒ `[build] ≠ [build,build]`、`[build,lightning] == [lightning,build]` |
| ③ | `_positions_for` | 按**类**跟踪"该类最后那个位置"（上一轮为绕开塌缩而改） | 按**形状**索引 + 每形状独立推进：`cursor[形状]={"t","pos"}`，第 t 步 = 各槽名次按**混合进制**展开 `rank_i=(t//Π_{j<i} n_j)%n_i`（槽 0 变化最快）⇒ 步 0 = 全体 argmax，之后逐格推进、穷尽全部组合（`np.argpartition` 只取第 k 名） |
| ④ | `generate` 的 `_advance_shape` | 命中缓存 = **跳过**（只 `continue`） | 命中 = **复用缓存分数 → 计入对应类 `Q[c]` → 游标已推进一格 → 继续试下一个位置**，直到解出新 bundle 或该形状位置穷尽（穷尽 ⇒ 记 `dead`） |

配套（不影响语义，只为可诊断/可复现）：
* 类采样的随机流由 **状态指纹**（`action_map` bytes + player）种子化 ⇒ 同局面同候选（可复现、不依赖调用顺序）；`AZAI_CAND_SEED` 可覆盖。
* 新增步数预算 `AZAI_CAND_STEPS`（每形状每次尝试最多推进几格，默认 **12**）与
  `AZAI_CAND_STEPS_TOTAL`（每次决策的位置推进总步数，默认 **max(1024, 16k)**）；超预算就退出。
* 新增读数：`缓存命中/步数/形状/穷尽形状/重复类形状/同类型多 op/Q 条目`，`AZAI_CAND_VERBOSE=1` 每决策打一行。
* 无位置的类（HOLD / 21 / 22）在多重集里出现几次就占几个槽，`n_i = 1` ⇒ 该槽不随步数变化（单位置臂）。

**零影响相关文件仍未动**：`bundle_mcts.py` / `decoder.py` / `network.py` / `flat_rollout_greedy.py`
（本轮一个字节都没改；`az_bridge_ai.py` 只多打印 `tau/steps/steps_total` 两个环境变量值）。

### 2.5 结论（回答用户的问题）

**塌缩的真因 = 经济限制（金币买不起），不是多重集索引。**

1. **单变量对照**（§2.4，最强）：同一个牌面，只把金币从 29/68/99/45/47 推到 ~600
   ⇒ `n_cand` **4→48、25→48、33→48、25→48**，合法类 2–21 → 23，oracle 3–855 → 1120。
   金币是唯一改动量，候选数就跟着打满 ⇒ 主因是**钱**。
2. **多重集索引不塌**：所有"金币充足"的局面（本轮 §2.4 推高后 4/5、§2.3 后手座位 5/5）都
   `n_cand = 48 = k`，且其中 25–33 条是**同 op 类型多 op**（`[build,build]` 等）——
   这正是"按多重集 + 允许重复类"才可能出现的候选。
3. **第二位的限制是"步数预算"，不是索引方式**：mid-coin 局面（金币 68–99）的单 op 空间
   （oracle）有 **558–855** 条，而 1024 步只枚举到 25–37 条（大量别名：16 个塔通道在同一空格
   解码成同一个 `BUILD_TOWER`），把总步数提到 1536 就变 23–42（`collapse_probe_p0_bigbudget.log`）。
   ⇒ 想更满就加 `AZAI_CAND_STEPS_TOTAL`，与"按类还是按多重集"无关。
4. 上一轮"7 条 / 426 次重复"= **穷局 + 小步数预算**的叠加：那时每形状 6 格、总 384 步。
   本轮把步数上限提到 1024、每形状 12 格后，冒烟里**"池≤7 且缓存命中≥400"的决策数 = 0**（§3.4）。

### 2.6 顺带验证：LogSumExp 对重复同值是否敏感（修正 ④ 的前提）

`Q[c]` 在缓存命中时会被重复计入同一个分数。公式 `LSE=(1/β)log(mean exp(βx))` 对**重复同值**的
影响 = 把均值往该值拉近（不是"撑大"）：

```
beta=1.0: LSE[0.30,-0.10,0.05] = +0.0971；补两个重复 0.30 → +0.1833（变化 +8.6e-2）
beta=3.0: LSE[0.30,-0.10,0.05] = +0.1248；补两个重复 0.30 → +0.2062（变化 +8.1e-2）
beta=8.0: 同方向、幅度更小（+6.0e-2）
```

即"重复计分 = 让该类的软最大更靠近'被重复的那个分数'"，**方向与'这类里确实有这么多观测'一致**，
不会像"求和"那样无界膨胀；`N[c]`（UCB 的分母）走的是"被选中次数"，与 Q 条目数解耦。
另外可看到 `Q条目`（Σ|Q[c]|）在富局是 1269–1617，而池只有 72 —— 这正是"缓存命中也在计入 Q"的
直接读数（若命中被跳过，这个数只会 ~池大小 × 束长 ≈ 150）。

## 7. 追加修正（2026-10-30 第二轮）：Q[c] 利用项改**玻尔兹曼加权** + 信用分配的 `1/|束长|` 折扣

> 依据：设计 `docs/unified_cand_design_20261029.md`（commit `b751351` §"Q[c] 利用项" 与
> §"信用分配（多动作束）"）+ 调研 `docs/prior_art_unified_search_20261030.md`。
> 只改 `code/my_ai/az_intent/unified_cand.py` 两处；其余（游标按多重集、候选键带重数、
> 缓存命中复用+推进、τ=1.0）**保持 `23d1490` 不动**。

### 7.1 改动 1：`_lse`（mellowmax）→ `_q_util`（玻尔兹曼加权平均）

| | 公式 | β=3、`x=[1.0,−1.0×9]` 时 |
|---|---|---|
| 旧（mellowmax / LogSumExp） | `(1/β)·log((1/n)Σexp(βx))` | **0.2398** |
| 新（玻尔兹曼加权，温度 softmax 当权重） | `Σᵢwᵢxᵢ`，`wᵢ=exp(βxᵢ)/Σⱼexp(βxⱼ)` | **0.9564** |

为什么换：mellowmax 带折扣 `log(n)/β`，而折扣**最大恰在"一个神手 + 一堆垃圾"**的情形
（正是我们最想突出神手的时候），方向与意图相反；玻尔兹曼加权没有 `log(n)` 项。
β 仍是纯温度旋钮（β→0 ⇒ 均值、β→+∞ ⇒ max），默认 **3.0** 不变。
数值稳定写法：先减 max 再 exp 再归一（`w ∝ exp(β(x−m))`），加权求和。

代码：`UnifiedCandidateGen._q_util`（`_ucb` 的利用项改成调它）。`_lse` 这个名字**没有留下**
（避免"名字叫 LSE 实际是别的公式"的误读）。

### 7.2 改动 2：信用分配 —— **最终定为完整回写（不打折扣）**（用户定夺）

```python
# 最终实现（= `23d1490` 的原样，本轮**没改**）：
for c in shape: self.Q[c].append(float(score))
```

中间曾按设计草案实现过 `share = score / max(1, len(shape))`（`1/|束长|` 折扣），
**已按用户定夺回滚**。语义理由：

* `Q[c]` 的定义是"**含 c 的动作组最好能有多好**"。例：`[build, lightning] = 1.2`
  ⇒ "含 build 的最好的组"和"含 lightning 的最好的组"**都应该是 1.2**，而不是各 0.6。
* `1/|束长|` 折扣会把它退化成"c 的**平均边际贡献**"，与上述语义矛盾，还会把
  **只靠组合才强的类**压下去（漏掉好组合）。
* 完整回写不会扭曲选择：`Q[c]` 只影响**探索分配**，最终 top-k 仍按阶段 1 rollout 分选，
  软最大天然容忍少量虚高分；`N[c]` 的记账在 `_pick_group`（与 Q 条目数解耦，**不拆 N_seen/N_eff**）。
* 顺手把 `_credit` 从 `generate` 内的闭包提成**方法**，好让它可被单测直接调用。

> 说明：本轮唯一真正落地的算法改动就是 **7.1（玻尔兹曼加权）**；信用分配保持 `23d1490` 的完整回写。
