## 0. TL;DR

1. **造了一个进程内快竞技场**（C++ 权威引擎 + Python 策略，**60-77 局/秒 / 6 进程**）。
   128 局一臂 ≈ 2 秒。项目历史上所有 A/B 都是 bridge 对局（**实测单局 1900-3900 s**、
   8-16 局/臂、血差 95%CI ±8-9）——现在同样时间能跑 **一万局**，血差 CI 收窄到 **±1 HP**。
   这是本次最有用的工具性产出。
2. **246 局自对弈的逐币账本**（引擎确定性重放，`.replay.json` 的 seed+ops 逐位可重建）：
   每局（双方合计）收入 **2418** 币，花在 `build 4208 / refund 4328 / upgrade 1669 / weapon 848 /
   base 0` ⇒ **净留存 ≈ 0**，即"赚多少花多少"；决策时刻金币中位数只有 **31**，**能掏出 90 币的回合只占 3.9%**。
   ⇒ **现役智能体是"没钱放闪电"，不是"不想放闪电"**。
   （顺带推翻一个流行说法：建塔↔降级 churn 的**净**花销是 **−119 币/局**，它几乎不烧钱；
   真正烧掉的是循环上的 10% 手续费 ≈ **480 币/局 = 收入的 19.9%**。）
   **2b. 把金币和选择对齐之后，链条闭合了**：70.8% 的决策发生在金币 <45（升级/闪电都不可能在菜单里），
   96.2% 发生在 <90（闪电不可能在菜单里），"合法类只剩 {降级,HOLD}"占 **73.8%**；
   而**金币 90-199 时闪电一旦进菜单就会被选 54.3%**——所以**不是评估器讨厌闪电，
   是"45-89 时优先升级 → 立刻变穷 → 闪电永远买不起"**。
3. **策略轴扫描（N=192/臂，9792 局）**：`武器=无` ⇒ **−21.9 HP / 胜率 7.3%**；
   `建塔预留 300 币` ⇒ **+7.7 HP / 68.8%**；`升级预留 120` ⇒ **+5.9 / 74.0%**；
   把塔升到三级（200 币）⇒ **−5.6 ~ −6.0**；多造塔（3/4/5 座）⇒ 略负。
   **钱花在闪电之外的每一处，都是负收益。**
   补充（§5b + §5c 稳健性检查）：升级的**时机**比升级本身重要——
   "打残才升级" **+5.0~+5.6** / "从不升级" **+3.5~+4.6** / "有钱就升级" **−0.6~+1.9**。
   ⇒ **"无条件升级是最差的选择"两批 seed 都成立**；但"打残才升级"与"从不升级"只差 ≤1.5 HP
   （镜像噪声 ±1.9），**分不出来**。冠军每局 33 次升级 + 32 次降级说明它两条都做，
   但那**不等于**"修理"能给我们 +6 HP。
4. **迁移检验（192 局/项，全胜）**：最佳策略 vs 不放武器的版本 **+29.0 HP / 100%**；
   vs 我们的"旧风格"（3 塔 + 猛升级） **+22.9 / 95.3%**；vs 只放闪电不建塔 **+7.6 / 71.4%**；
   vs 什么都做 **+30.7 / 100%**。⇒ 不是"打赢了一个弱参照"，是**在三种不同风格上同向**。
5. **塔位**：33 个可建格点的贪心穷举（每步 33 臂 × 96 局）⇒ **默认顺序（=离自己基地最近的格）已经是最优**，
   任何"先建在别处"都要付 **−2.4 ~ −4.8 HP**。原因：所有蚂蚁都必须经过基地门口，
   近基地的位置覆盖**全部**进攻路线；前压塔只覆盖一条。
6. **冠军对照（旧 pin 配置的 16 局，只读日志）**：我们**先掉血的回合中位数 23.5**，冠军 **53.5**（16/16 局都是我们先掉）；
   我们 **0 次升级**、冠军 **33 次升级 / 32 次降级**（≈ 每 13 回合一次升级+降级）；
   双方都在**满地图搬塔**（每局 ~100 次建 + ~100 次拆，33 个格点全会用到）。
7. **历史对照（必须先看，别当新发现）**：2026-09-19 的 `rv4_lightning_only` 已经测过
   "只放闪电 17.2% vs 完整 rule_v4"、"只建塔 0%"、"两者都做最强"；2026-10-07 的
   `B90_buildgate_64`（`AZAI_BUILD_MIN_COINS=90`，**+4.7pp**，机制"建塔 24.8→16.7、闪电 10.5→11.1"）
   和 `L180_reserve_64`（闪电储备门槛 **−45.3pp**）已经指出"边际金币应该给闪电"这条轴。
   **我的增量不是"发现闪电强"，而是：
   ① 把它放到一个 N 大、单变量、对照干净的台子上，量出"闪电 vs 塔/升级"的兑换率（≈5-10 倍/币）；
   ② 指出这与现役的花钱结构（69% 收入给升级）直接冲突；
   ③ 补上历史上没测过的"条件升级"：无条件升级 −0.3 / 从不升级 +3.2 / **修理式升级 +5.8**；
   ④ 直接验证"网络裸策略本来就是攒钱+闪电"（只比调优规则差 1.5 HP）⇒ 现役的过度花钱
   是**评估器**造成的，不是先验。**

## 1. 工具：进程内快竞技场

`code/test_match/fast_arena.py`

```
Policy = callable(state, player) -> list[Operation]
引擎   = GameStateFacade（官方 C++ 引擎 pybind 封装，cold_handle_rule_illegal=True）
座位   = seed 偶数 A 当 P0，奇数 A 当 P1（镜像配对，消掉先手）
指标   = 终局血量差 margin（A 视角）+ 胜率；同时记录每局 op 构成（闪电次数/建塔次数）
```

实测速度（6 workers）：`noop vs noop` 36 ms/局、规则策略 ~60-90 ms/局，端到端 **60-77 局/秒**。

为什么这件事重要：
| | bridge 对局（历史） | 快竞技场（本次） |
|---|---|---|
| 单局 | 10-20 min | 0.05-0.1 s |
| 一臂样本 | 8-16 局 | 96-512 局 |
| 血差 95%CI | ±8-9 HP | ±1-2 HP |
| 能分辨的效应 | ≥10 HP | ≥1 HP |

> 局限（必须一起读）：它只装得下"便宜的"策略（规则 / 网络 argmax，**不能**装 flat-rollout 搜索）。
> 所以它量的是**策略层**，不是"现役智能体的网络+搜索"。要把现役搬进来，见 §8 建议 C。

## 2. 逐币账本：钱从哪来、到哪去（246 局）

`code/test_match/explore_money_flow.py`：把 `training_history/collect_v2_s1/*.replay.json`
（seed + 每回合双方完整 ops）在 C++ 引擎里重放，**逐个 op 记金币增量**（build 花多少、downgrade 退多少、
升级/武器/base 各多少），结算阶段的金币变化单独记成 income。

每局（**两名玩家合计**，平均 337 回合）：

| 项 | 金币 | 占收入 |
|---|---|---|
| 结算收入 income（基础 1.5/轮 + 击杀 + 到达） | **2418** | 100% |
| 建塔 build（毛） | 4208.5 | — |
| 降级退款 refund（毛，正） | −4327.7 | — |
| ⇒ 建/降循环**净**支出 | **−119.2** | −4.9% |
| 升级 upgrade | **1669.0** | **69.0%** |
| 超级武器 weapon | 848.3 | 35.1% |
| 基地升级 base | **0.0** | 0% |
| 净留存（≈终局金币−初始） | +19.9 | ≈0 |

关键读数：

- **收入里只有 42% 是基础收入**（1.5/轮 × 337 = 505），其余来自击杀与"蚂蚁到达敌方基地 +10"。
  也就是说**进攻本身是收入来源**——这解释了为什么"守得住"比"省着"更值钱。
- **现役把 69% 的收入花在升级上**，35% 花在武器上，塔本体净支出 ≈ 0，终局只剩 109 币。
- **金币中位数 31，p90=68，能掏出 90 的回合只占 3.9%，能掏出 200 的占 0.0%**。
- **"钱够 90 且闪电 cd=0 却没放"** 每局只有 8.5 次（1.3% 的回合）⇒ **不是决策问题，是没钱**。
  真正的"错过"是 **升级**：每局 64.7 次（9.6% 的回合）钱≥60 且有塔却没升级——这条我下面会说它反而是"对的"。
- **基地升级 246 局 0 次**；**EMP 246 局 6 次**；闪电 6.49/局（=3.25/人/局），
  而 cd 35 + 337 回合 ⇒ **每人理论可放 ~9.6 次**。
- 塔数：均值 **2.30**、中位 2、峰值 5，97.8% 的回合至少 1 座塔。
- churn 的真实代价：**退款 4327.7 是从 4808.5 的毛投入退回来的（×0.9）⇒ 循环手续费 480.8 币/局 = 收入的 19.9%**。
  它不体现在"净支出"上，但**每一枚循环过的币都被抽了 10%**。
  ⚠️ 口径说明：`refund` 里**包含"降级已升级的塔"退回的那部分升级费**，所以
  "build 毛额 − refund 毛额 = −119"**不能**读成"建塔净赚 119"；它只说明"钱在塔和金币之间几乎全额往返"。
  真正能加总的分解是：`收入 2418 = 升级 1669 + 武器 848 + (build−refund) −119 + 净留存 20`。
- 与历史文档的差别：`unified_rootcause_deepdive_20261101.md` 把"降级 churn 烧钱"作为主因。
  从账本上看，churn 的**净**花销是负的（甚至"赚钱"），它真正的代价是 19.9% 的手续费 +
  每次拆塔那 1-2 回合的裸奔 + 塔血重置。**"churn 烧钱 → 变穷"这条因果链在钱上不成立；
  变穷的直接原因是"升级吃掉 69% 收入"**（并且见 §2b：升级发生在 45-89 币区间，正好把你按在穷态里）。

## 2b. 把"金币"和"选择"接起来：**贫穷陷阱是真的，而且比之前写的更彻底**

`code/test_match/explore_poverty.py`：把 252 局 replay 在引擎里重放，**在每个决策时刻记下真实金币/塔数**，
再与同局的 `cand.jsonl`（候选 + s1/s2 + `Q` 的合法类集合）按 (round, player) 对齐（170,348 个决策）。

| 金币桶 | 决策占比 | 闪电在菜单 | 升级在菜单 | 降级在菜单 | HOLD 被选 | 合法类 ⊆{降,HLD} |
|---|---|---|---|---|---|---|
| <15 | 20.3% | 0.0% | 0.0% | 99.6% | 81.6% | **100%** |
| 15-44 | **50.5%** | 0.0% | 0.0% | 98.6% | 77.7% | 91.8% |
| 45-89 | 25.4% | 0.0% | 28.7% | 88.1% | 38.6% | 28.0% |
| 90-199 | **3.8%** | 46.1% | 69.7% | 89.1% | 24.2% | 0% |
| ≥200 | 0.02%（42 条） | 61.9% | 66.7% | 97.6% | 78.6% | 0% |

- **70.8% 的决策发生在金币 < 45 时**，那里 **升级和闪电都根本不可能出现在菜单里**（钱不够）；
  **96.2% 的决策发生在金币 < 90 时**，那里闪电不可能出现。
- **"贫穷陷阱"（合法类只有 {降级, HOLD}）占 73.8%**，与深挖文档的 73.6% 一致（我这是独立重放的独立算法）；
  这些决策时的金币 mean 25.2 / median 24 / **max 59**。
- **关键修正**：**不是评估器讨厌闪电**。金币 90-199 时，闪电在菜单里的概率 46.1%，
  **一旦在菜单里，它被选中 54.3%**。同一桶里升级的 s2 排名百分位是 **0.905（几乎总排第一）**。
  ⇒ 链条是：**有钱（45-89）时评估器优先升级 → 立刻变穷 → 掉进 <45 的"只剩降级/HOLD"状态 → 闪电永远买不起**。
  这解释了为什么"闪电次数"与胜负强相关**而**"直接改网络/改先验让闪电更香"没用：
  **闪电不需要更香，需要的是"别在 45-89 就把钱花光"**。
  这也正是 2026-10-07 `AZAI_BUILD_MIN_COINS=90` 拿到 +4.7pp 的真实机理（它把 AI 挡在穷态之外）。

**三条可检验的读数：**

1. **闪电是"最强的一枚币"**：拿掉它 = −21.9 HP（本表最大的单项效应，比项目历史上最大的
   "+12 HP 注入效应"还大）。而"什么时候放"的阈值 k=3 附近是**最优平台**（k=2 −2.0、k=4 −6.9、
   k=5 −16、k=8 = 从不放 −21.7）。"只在自己半场放"（dist=6）反而 −9.4 ⇒ **要在蚂蚁还远的时候就打**
   （闪电每回合 20 伤、持续 15 回合，越早放覆盖的波次越多）。
2. **一切"花钱"的旋钮都在和闪电抢钱**：造塔、升级、基地升级、迁塔、别的武器，全是负的；
   而"多留钱"（build_reserve / upg_reserve）全是正的。**效应大小可以按"抢走了几次闪电"解释**：
   三级塔 200 币 = 2.2 次闪电；`n_towers` 3→5 的边际塔 135-270 币 = 1.5-3 次闪电。
3. **塔的收益是"有就行"**：n_towers=0 只比 n_towers=2 差 0.7（不显著），n_towers≥3 反而更差。
   和"塔数均值 2.3"这条对得上——**但现役把钱花在升级上，等于用 2 座塔的价格买了一座塔的防御**。

> `weapons=light+defl/evas/emp` 那几行**不能**读成"这三个武器没用"：我的实现里它们是"能放就放"，
> 60/135 币的施法把金币抽干（闪电次数掉到 1.8），所以测的是"抢钱"的代价，不是它们自身的效果。
> 这是一个**已知的实现缺陷**，见 §7 待办。

## 5. 塔位：33 个格点穷举（每步 33 臂 × 96 局，3 步）

`explore_strategy_sweep.py greedy`。因为 P0/P1 的**可建区域形状不同**（见 §6），
我用「`STRATEGIC_BUILD_ORDER[player]` 的下标」作为座位无关的位置编码（idx 0 是基地格、不可建；
可建 = idx 1..33）。

- 第 0 位：**idx=1（P0: (4,9) / P1: (14,9)）最好**（margin −0.31 vs 参照 0.00）；
  任何别的首塔位置 **−2.39 ~ −4.79**（idx=7/5/3/20/12/8/6…全负）。
- 第 1 位：**idx=2（(5,9)/(13,9)）最好**；换成 idx=7/5/3 要付 −2.1 ~ −2.4。
- 结论：**"离自己基地最近的两个格"就是最优开局**，官方 `STRATEGIC_BUILD_ORDER` 的顺序
  （去掉不可建的前两格）**已经是最优**，贪心搜了 3 步一步也没改进。
  机理解释：所有蚂蚁都必须经过基地门口，近基地的塔覆盖**全部**进攻路线；前压塔只覆盖一条。
- 效应量：塔位整体跨度 ~5 HP ⇒ **塔位是真实但次要的杠杆**（闪电是 22 HP 量级）。

对照：现役/冠军**实际**用的塔位分布（`explore_cells.py`，把坐标统一成下标）：
- **双方在 16 局里都用遍了全部 33 个格点**（每格 ≈ 每局一次）⇒ 实战不是"选点"，是**满地图搬塔**。
- 现役的"开局第一座塔"分布很散：idx20 (8,11) 23.5%、idx16 (4,2) 16.3%、idx24 (6,1) 10.4%、
  idx32 (8,2) 8.6%、idx25 (6,2) 8.4%…，与"近基地最优"不一致（它更爱往前压）。
- 冠军的建塔分布几乎均匀（16 局 × 每格 16 次），看不出偏好。

> 诚实声明：塔位结论是在 `n_towers=2` 的规则策略上量的；如果塔多到能覆盖多条路线，
> 前压可能重新有意义。这条要按"少塔 + 攒钱"的配置一起用。

## 5b. 机制实验：把"升级"当**修理**用（96 局/臂）

`code/test_match/explore_repair_mechanic.py`（新增 `upg="damaged"`：只在塔血量比 ≤ 阈值时才升级，
利用"升级回满血"当廉价修理）：

| 臂 | margin | ±se | 胜率 | 闪电/局 | 终局金币 |
|---|---|---|---|---|---|
| always_br300（= §4 最优，几乎不升级不建塔） | +7.44 | 1.44 | 67.7% | 10.59 | 268 |
| **damaged40（血量≤40% 才升级）** | **+5.79** | 1.10 | 70.8% | 10.64 | 208 |
| **repair_cycle60（打残才升级，且下一回合降级退回）** | **+5.72** | 1.06 | **77.1%** | **10.85** | **267** |
| damaged80 | +5.67 | 1.30 | 72.9% | 10.12 | 185 |
| damaged60 | +5.00 | 1.24 | 66.7% | 10.21 | 191 |
| repair_cycle40 | +4.33 | 0.99 | 69.8% | 11.12 | 247 |
| upg=never | +3.16 | 0.90 | 62.5% | 11.17 | 222 |
| *ref（有钱就升级）* | *−0.31* | — | 51.0% | 8.94 | 183 |

⇒ **升级本身不是坏事，"有钱就升级"才是**：同样是 60/200 币，
"被打残才升级"比"从不升级"多 **+2.6 HP**、比"有钱就升"多 **+5.8 HP**，而且闪电次数不掉（10.6 vs 8.9）。
再加上完整的**修理循环**（升级回满血 → 下一回合降级退回 90%）：**+5.72 / 胜率 77.1%**，
终局金币反而更高（267 vs 183）——**净成本只有 6 币/次**（引擎实测：60 花出、54 退回）。
这条和冠军的行为完全对得上（每局 **33 次升级 + 32 次降级** ≈ 一直在修塔）。
**所以 §3 的"升级是负的"要精确化成："无条件升级是负的；不打钱的时候（从不升级或打残才升级）都更好"**。

**稳健性检查（换一组全新 seed 90000+，N=192/臂，`explore_robustness.py`）**——这一步很重要，它把两条结论打了折：

| arm | 主表 seed 2000+ | 新 seed 90000+ | 结论 |
|---|---|---|---|
| ref vs ref（镜像 sanity） | −0.58 ±0.99 | **+1.85 ±0.99** | 镜像本身的噪声 ≈ **±1.9 HP** ⇒ **<2 HP 的差异不可分辨** |
| weapons=none | −21.89 | **−23.36** | 稳（−22 ~ −23） |
| build_reserve=300 | +7.72 | **+8.51** | 稳（+7.7 ~ +8.5） |
| upg=never | +3.47 | **+4.60** | 稳（+3.5 ~ +4.6） |
| upg=damaged60 | +5.00 | **+5.62** | 稳（+5.0 ~ +5.6） |
| repair_cycle60（+br100） | +5.72 | **+4.29** | **不稳**：两批里"比 upg=never 好 +2.6 / 差 −0.3" ⇒ **修理循环 vs 从不升级 分不出来** |

⇒ 可以放心讲的是：**"别无条件花钱"（build_reserve / upg=never / upg=damaged 都比 upg=always 好 4-8 HP）**；
**不能**讲"修理循环一定比从不升级强"（两批符号相反，量级 ≤1 HP，落在镜像噪声里）。
"修理循环"最多算**机制上优雅、成本 6 币**（§8-B），不是已证实的强度来源。

**联合网格（192 局/臂，`GRID_ONLY=1`）**——把"修理循环 × 攒钱 × 塔数"一起扫：

| 臂 | margin | ±se | 胜率 | 闪电/局 | 建塔/局 |
|---|---|---|---|---|---|
| **rc60 + build_reserve=100 + n_towers=2** | **+5.88** | 0.73 | **75.0%** | 10.84 | 17.4 |
| rc60 + br100 + n3 | +5.73 | 0.73 | 74.5% | 10.79 | 18.3 |
| rc60 + br300 + n3 | +3.43 | 0.77 | 65.6% | 10.88 | 7.2 |
| rc60 + br100 + n1 | +3.34 | 0.69 | 69.8% | 10.60 | 10.0 |
| rc60 + **br0** + n2 | **−8.73** | 1.24 | 38.5% | **6.58** | **26.3** |
| rc60 + br0 + n3 | −17.51 | 1.18 | 19.3% | 3.67 | 27.1 |

⇒ **"修理循环"和"留钱"必须一起用**：不留钱（br0）时 build 暴涨到 26/局、闪电掉到 6.6 ⇒ **−8.7**；
留 100 就把闪电拿回 10.8 并变成 **+5.9 / 75.0%**。

**头对头 sanity（128 局）**：`bestv2`（修理循环+br100）vs `best`（br300、几乎不建不升）= **−3.08 ±1.14**
⇒ 三者是**一致的三段序** `best(+7.7) > bestv2(+5.9) > ref(0)`，没有非传递性。
但也说明一件事：**在"双方都是便宜规则策略"的世界里，最优是"几乎什么都不买、只买闪电"**
（因为这种对局里塔的边际价值低）。而现实对手（冠军 / rule_v4）会真的压上来，
历史上的 `rv4_lightning_only = 17.2%`（只放闪电 vs 完整 rule_v4）说明**真对手面前塔是必需的**。
所以可交付的结论应该这样分层：
- **主轴（决定性）**：边际金币给闪电，不要"有钱就升级/建塔"；
- **次轴（保留塔时必须做对）**：塔要**修理**（打残才升级、修完退回），不要一有钱就升级。
**可交付规则（一条）**：
`1-2 座塔；建塔要求 coins ≥ cost+100；只在塔血量 < 60% 时升级并在下一回合降级退回；`
`coins≥90 且 cd=0 且敌方蚂蚁有 ≥3 只在半径 3 内 ⇒ 立刻对最密的集群放闪电`。
（这个配置在竞技场里比"典型规则策略"高 **+5.9 HP / +25.5pp 胜率**，N=192。）

## 6. 顺手量到的两件事（影响所有 A/B 的读法）

### 6.1 两个座位玩的**不是**同一张图

- 每方 33 个可建格点，两个集合**各自**都关于 `y → 18−y` 对称；但**没有任何**
  `(±x+ox, ±y+oy)` 变换（含奇偶列 ±3 行的偏移）能把 P0 的区域映到 P1（最大重叠 22/33）。
- 屏障/虚空同样只有 `y → 18−y` 这一个对称。
- 实测座位效应（`explore_seat_effect.py`，各 512 局镜像）：
  `ref vs ref`：A=P0 margin **+0.49**，A=P1 **−0.70**（合并 −0.10 ± 0.61）⇒ **HP 上没有座位偏差**；
  但**胜率** A=P0 52.0% / A=P1 47.3%；`noop vs noop`（双方都不动）**P0 胜率 57.4%**、margin 只差 +0.34。
  ⇒ **平局链最后一条是"先手胜"，所以镜像局本身就偏向 P0 ~+7pp**（在"双方都不动"这种最平的局面里最明显）。
- 实践含义：**8 局/臂的 A/B（4 seed × 2 座位）在 HP 口径上是干净配平的**，但
  "胜率"口径里有一个 ~+5pp 的先手常数；另外两个座位是**两张不同的图**，
  所以配对只在"同一座位内"成立，跨座位不是严格的镜像。

### 6.2 我们 vs 冠军（旧 pin 配置的 16 局，只读 trace 日志）

`explore_champion_profile.py` 解析 `match_results/champion_e1/stderr/ai*_az_bridge_ai_seed*.stderr.log`
的逐回合 trace（hp / 双方金币 / 我方塔(含类型) / 对方塔(含等级)）：

| | 我们 | 冠军 |
|---|---|---|
| 先掉血的回合（中位） | **23.5** | **53.5** |
| 升级 / 降级 次数每局 | **0 / 0** | **33.1 / 32.7** |
| 建塔 / 拆除 次数每局 | 97.2 / 95.9 | 102.6 / 101.2 |
| 塔数均值 / 峰值 | 1.57 / 3 | 1.80 / 3 |
| 金币均值 / ≥90 回合占比 | 70.4 / 27.5% | 65.8 / 25.6% |

- 双方都在**满地图搬塔**（每局 ~100 建 ~100 拆，峰值 3 座）⇒ "移动防御"是这局游戏的常态，不是病。
- 唯一大差别是：**冠军每局做 33 次升级 + 32 次降级，我们 0 次**。

### 6.3 网络裸策略 vs 规则策略（把 ML 栈接进竞技场）

两个必须一起读的事实：

1. **网络裸策略基本"不造塔"**：16 局里双方合计 0.28 座塔。原因已知（`docs/why_no_upgrade_20261028.md`）：

2. **但这个"退化"策略只比调优后的规则策略差 1.5 HP**（且比 `upg=never` +3.2 / `damaged*` +5~6 / `best` +7.4

   而在"评估器把先验的好直觉改坏了"**。

   `rv4_lightning_only`：只放闪电对完整 rule_v4 只有 17.2%。所以这条是**机制线索**，不是"现役该关掉搜索"。）

### 6.4 评估器到底把什么判成正分（169,730 个决策的离线体检）

`code/test_match/explore_eval_bias.py`（252 局 cand.jsonl；每条决策都带
`s1`=阶段1 idle+值网、`s2`=阶段2 random rollout、`chosen_idx`）：

| 被选中的动作 | 占比 |
|---|---|
| HOLD | **66.5%** |
| 建塔 | 15.7% |
| 降级 | 12.9% |
| 升级 | **4.0%** |
| 闪电 | **0.46%** |
| 偏转/回避/EMP | 0.31% / 0.13% / 0.002% |

- **最终选择 = s2 的 argmax**（每一类都逐位吻合），所以"决策 = s2 说了算"。
- **s1 与 s2 的 top-1 有 42.7% 不一致**——两套评估器打架的比例非常高。
- **头对头（该类在菜单里时，top-1 落在该类的比例）**：

| 类 | 出现在多少决策 | s1-top1=该类 | s2-top1=该类 | best_s1−chosen | best_s2−chosen |
|---|---|---|---|---|---|
| HOLD | 169,730（100%） | **51.0%** | **66.5%** | −0.0121 | −0.0129 |
| 闪电 | 8,457（5.0%） | 17.3% | 19.3% | −0.0270 | −0.0446 |
| 升级 | 225,979 | 3.0% | 3.1% | −0.0099 | −0.0389 |
| 降级 | 1,158,095 | 4.8% | 2.4% | −0.0211 | −0.0416 |
| 建塔 | 1,002,091 | 2.8% | 2.7% | **+0.0300** | −0.0065 |
| 偏转 | 66,121 | — | — | — | — （排名 pct 0.42，几乎总被否） |

**读法（三条，都是可检验的）**：
1. **passivity 是 rollout 层放大的，不是值网的锅**：HOLD 在菜单里时，
   值网（s1）只有 **51.0%** 会选 hold，而 rollout（s2）选 **66.5%**——而最终跟 s2。
   ⇒ 想把"该动的时候动起来"，**要改的是 s2（flat rollout 的对手模型/打分），不是再训值网**。
2. **闪电"进了菜单也常输"——但按金币分桶后这个结论要改**：全体平均是 19.3%，
   而**金币 90-199 桶里它一旦在菜单里就有 54.3% 被选中**（§2b）。
   差别来自"候选生成用的是 intent 解码（不查金币）"：钱不够时也会生成 `[21,x,y]` 候选，
   它们在 `can_apply_operation` 那一步被丢掉。⇒ **闪电的瓶颈是"买不起"，不是"评估器不喜欢"**。
   （这也是两个脚本口径不同的地方，以 §2b 的按桶分析为准。）
3. **s1 与 s2 在"建塔"上的符号相反**：s1 的 `best_build − chosen = +0.0300`（值网想建），
   s2 是 −0.0065（rollout 不想建）⇒ **建塔 15.7% 的最终执行是两套评估器互相抵消的结果**，
   这也解释了为什么"改值网/改先验"在这条轴上总是零效应：**被下游 s2 否决**。

## 8. 我认为最值得做的（排序）

**A（最高性价比，今晚就能做）——把"钱花在闪电上"变成现役能用的东西。**
现役的短板是**金币被升级吃掉**（69%），闪电只能放 3.25 次/人/局（理论 9.6）。
§2b 把机制钉死了：**96.2% 的决策发生在金币 <90 时（闪电根本进不了菜单）**，
而 45-89 币区间升级的 s2 排名是 0.905（几乎必选）⇒ **"有钱就升级"把 AI 按在穷态里**。
建议做一个 **3 臂 A/B（对手 rule_v4，8 局/臂，镜像座位）**：
1. `base`：现役；
2. **"省钱"臂**：把升级候选的触发条件改成"塔被打残才升级"（§5b：竞技场 +5.8 的直接证据），
   或先用手上现成的执行层开关 `AZAI_BAN_OPS=12`（把选中的升级删掉 ⇒ 该回合 HOLD，有混淆）；
3. `省钱 + 强制闪电`：再加 `AZAI_INJECT_COIN_RULE=1, hold_lo=90, cd=0, p=1.0`
   （这套接口已经在 `az_selfplay`/bridge 里，只是默认关；`_tmp_rv4_lightning_only.sh` 用过它的雏形）。
判据先登记：**闪电次数 ≥2 倍、终局金币上升、血差 ≥ +5**。
⚠️ 另一条独立证据（§6.3）：**网络裸策略（argmax、无搜索）本来就是"攒钱 + 放闪电、不造塔"**，
在竞技场里只比调优规则策略差 1.5 HP ⇒ 现役的"升级 69%"不是先验的主意，**是评估器改坏的**。
所以这条 A 实验真正在问的是：**把"45-89 就花光"这条习惯改掉，能拿回多少？**

**B（机制层，几乎没人碰过）——"升级→降级"当修理/换型。**
冠军每局 33 次升级 + 32 次降级。规则上"升级回满血"，"降级退 90%×血量比例"⇒
**6 币即可把一座 1/10 血的塔修满**（引擎实测：60 花出、54 退回，塔满血、类型回原样）。
竞技场结果（§5b，N=96/192）：
`upg=damaged`（打残才升级）**+5.79 / 70.8%**；
**`repair_cycle`（升级回满血 → 下一回合降级退回）+5.72 / 77.1%**；
`upg=never` +3.16 / 62.5%；`upg=always` −0.31 / 51.0%。
联合最优 = **repair_cycle + build_reserve=100 + 2 塔 = +5.88 ±0.73 / 75.0%（N=192）**。
⚠️ 但 §5c 的换 seed 复核把这条打了折：**"修理循环 vs 从不升级"两批 seed 符号相反（+2.6 / −0.3）**
⇒ 只能确定"**无条件升级是最差的**"，不能确定"修理比不修强"。
⇒ 落地建议分级：
1. **先做 A（省钱门控）**——那是两批 seed 都稳的（+3.5~+4.6 HP，胜率 62-70%）；
2. 再把修理循环当作**廉价附加项**（净成本 6 币/次）加上去，它是"机制上正确、成本可忽略"，
   不是"已证实的强度来源"。实现只需候选门控：
   `if tower.hp < 0.6*max_hp and coins >= 60: 生成升级候选`，升级成功后下一回合生成降级候选。

**C（工程，让以后所有实验快 1000 倍）——把现役的策略搬进竞技场。**
现在已经能装"网络 argmax"（无搜索，`arena_net_policy.py`）。如果再补"网络 argmax + 一层
`mc_quiet`/小 rollout"，就能在**同一台子**上直接 A/B 现役的 `AZAI_CKPT`/`AZAI_CAND_MODE`，
不用 bridge、不用 30 分钟一局（本次实测 bridge 单局 1900-3900 s）。这一步做成之后，
"8 局/臂"的历史分辨率问题就永久解决 —— **这是我最想推荐的一条**。

**D（ML 方向，最贵，优先级被 §2b 下调）——给评估器喂"钱的时间价值"。**
原假说是"值网读不懂闪电"。**§2b 的数据否掉了一半**：闪电一旦买得起，54% 会被选中；
真正的问题是**从没富到买得起**。所以更该做的不是"让值网更喜欢闪电"，而是
① 让 **s2（flat rollout）的对手模型**别再把金币当零价值（历史机理：安静/随机 rollout 里
"金币在没人再出招的世界里没有价值 ⇒ 花钱看得见好处、看不见代价"）；
② 或者直接用**候选门控**加"钱的时间价值"（廉价版就是 A/B 两条规则）。
若仍想动网络：和 parent 的 E2（`hinge(coins−90)` / `coins×(1−cd/35)`）目标一致——
**让"攒到 90"这件事在评估里值钱**。

1. **EMP 的进攻用法没测出来**：我实现的 EMP 需要"我方蚂蚁已推到敌方塔群 6 格内"才放，

4. **塔位表在 `n_towers=2` 下量的**，塔更多时结论可能翻转（未测）。
5. **贪心塔位只搜了 3 步**，且第 3 步开始"没用"（`n_towers=2` 只建 2 座塔）——我一开始没意识到，

6. **冠军的塔型看不到**（trace 只记对方塔的坐标+等级，不记类型），所以"冠军爱升什么"未知。
7. **30 分钟级别的对局行为**（"每局 ~100 建 ~100 拆"）只在旧 pin 配置的日志里有；unified 配置下
   churn 是 125 次降级/114 次建塔每局，**两种配置的 churn 结构不同**，不要混着引用。

## 12. 三句话总结

**① 我自己发现了什么**：现役不是"不会用闪电"，而是**永远没钱用**——96.2% 的决策发生在金币 <90
（闪电根本进不了菜单），70.8% 在 <45（连升级都不可能），"合法操作只剩 {降级,HOLD}"占 **73.8%**；
而一旦有钱（90-199），闪电进菜单就有 **54%** 会被选中。钱是在 **45-89 区间被升级吃掉的**
（升级占 69% 收入）——同时账本推翻了"降级 churn 烧钱"（净 −119 币/局，真代价是 19.9% 的手续费）。
配套第二条：**策略层的杠杆比 ML 层大一个数量级**（竞技场 N=192/臂：拿掉闪电 −22 HP、少花钱 +7~+8.5 HP，
而历史上换值网/换先验都是 0-3 HP），而且**网络自己的裸策略本来就是"攒钱 + 放闪电、不造塔"**
（只比调优规则策略差 1.5 HP）⇒ **是 rollout 评估层（HOLD 66.5% vs 值网 51%）把好直觉改坏的**。

**② 我做了什么尝试**：造了一个**进程内快竞技场**（官方 C++ 引擎 + Python 策略，60-77 局/秒，
比 bridge 快 2-3 个数量级），在上面跑了约 **2.5 万局**策略实验（策略轴 9792 / 塔位贪心 9400 /
组合 4224 / 修理 2880 / 迁移 1152 / 换 seed 稳健性 1152）；用确定性引擎重放 246 局做了逐币账本、
行为画像、冠军同局对照、金币×选择对齐、评估器偏袒体检；另起了一个现役上的 `AZAI_BUILD_MIN_COINS`
侦察 A/B（8 局/臂预算，JOBS=2-3，每局 ~40 min，本文档定稿时只到部分局）。
**失败/被推翻的**：EMP/偏转/回避的实现太白痴，测不出价值；"前压塔位"被证伪（近基地最优）；
"修理循环比不升级强"换 seed 后不成立（≤1.5 HP，落在镜像噪声 ±1.9 里）；
"金币门控能复现历史 +4.7pp"在前几局上失败，且**机制没发生**（建塔 71→37，闪电仍是 6）。

**③ 我认为最值得的方向**：
(a) **把"钱的时间价值"塞进候选门控/评估器**（升级只在塔被打残时出候选；建塔要求 coins ≥ cost+100；
闪电走候选注入，不经 s2 评估）——三件都是几十行、可 A/B，且两批 seed 都稳（+3.5~+8.5 HP）；
(b) **工程上把现役策略搬进竞技场**（net argmax + 一层小 rollout），从此所有 A/B 从"8 局/小时级"
变成"128 局/秒"——这是我最想推荐的一条，它能把项目目前所有"测不出来"的问题一次性解决；
(c) 研究上查清 **s2（flat rollout）为什么把 HOLD 判得比值网高 15.5pp**（`s1/s2` top-1 分歧 42.7%，
10-07 的机理笔记"s2 里金币没有价值"现在可以定量解剖了）。
