# 异常吞噬审计（2026-10-22）

> 触发原因：`bundle_mcts.py` 里 `int('op')` 抛 `ValueError` 被宽 `except` 吞掉，导致
> **「升级塔」这个动作类自机制落地起一次都没被执行过**（对亚军 32 局 1,171 个 op 里升级 0 次），
> 而我们把现象错误归因为"值网不认可升级""需要重训""需要照抄亚军的硬编码奖励"。
> 之后修这一行时又漏了 `else` 分支的 `_ccls` 赋值，`NameError` 被**同一个** except 吞掉 ⇒
> 仲裁整体失效，8 局 51 个 op **全是闪电**。
> 同一个 `except` 在历史上已至少命中三次（`61333aa` 的 `UnboundLocalError`、`ce9beed`、本次）。

## 一、已修复（3 处，均已验证）

|---|---|---|---|---|

## 二、同批修复（可观测性）

- 仲裁宽 except 现在打印**首次**异常全文：`[mc] ⚠️ 仲裁异常回退（首次）：<类型>: <信息>`；
- 收尾报告无条件带 `mc_taken / mc_fallback / mc_err`（不再依赖计时日志开关）；
- `mc_last_explicit` 在**门控关闭 / skip / 异常回退**三条路径上复位（避免跨回合重发同一手升级）。

## 四、教训（写给以后）

1. **"某类动作/分支恒定为零"时，第一件事是去翻 fallback 计数器**，而不是先怀疑模型或数据。
2. **宽 `except` 至少要把异常内容打一次**（首次足够）。这次如果早有一条 `[mc] ⚠️ ...`，
   事故会在第一局暴露，而不是藏了整晚。
3. **不要用"两个错误互相抵消"的代码**：一旦只修一边，就会坏到另一个方向（本次 #3 就是这样）。
4. 计数器存在 ≠ 可观测：**读取计数器的代码本身也可能在抛异常**（本次 #2）。
