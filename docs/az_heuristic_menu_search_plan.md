# 计划：官方启发式 top-K 当候选菜单 + 价值网搜索选招（对局级判据）

> 日期：2026-09-19。**用户提出**（"用 example 的那个启发式评分选前 24 当候选，然后用价值网
> 络去 mcts 搜索选具体哪个动作，和直接选评分第一的动作打看看"）。状态：计划阶段，待过目。
> 前置：`docs/az_class_axis_plan.md` §5(a)（注入采集 + 重训价值网）。

## 1. 为什么需要这个（补上现有判据的短板）

现有判据 `_tmp_rank_quality.py` 量的是"**价值网挑的候选，在官方启发式排序里的分位**"。
它干净、无对局噪声，但**尺子本身弱**：

| 事实 | 出处 |
|---|---|
| k=96（≈全部候选）时官方 top-1 vs random = 0.6406（t=+2.06）| `cand_pick_k96` |
| **k=8 时官方 top-1 vs random = 0.4531（t=−0.90）** | `cand_pick_first` |
| 官方启发式当策略：**0:32 全败给 rule_v4**、闪电 0%、建塔 93% | `cand_pick_k96` |

⇒ 官方 score 的价值是"**筛出好的一小撮**"，不是"**排出先后**"。所以那个分位 = ①"有没有从
好的一端挑"（有信号）+ ②"有没有和好端内部的噪声一致"（没信号）混合。**它不能证明价值网好。**

**这个计划改用一个不依赖任何手写评分当尺子的判据：让两侧在同一份候选菜单里对打。**

## 2. 设计

**候选菜单**：两侧都从 `ActionCatalog.build()` 按官方 `score` 取 **top-K（K=24）**。
理由（用户，2026-09-19）：我们重训价值网**就是为了让它能判塔这类非闪电动作的好坏**，
而官方 top-24 里**大概率不含闪电**（此前实测 `first` 臂动作构成闪电 0%；用户确认不用再测）
⇒ **两侧都不会放闪电** ⇒ 这盘棋只在"建塔/升级/降级/经济"这条轴上分胜负，
**正好就是价值网唯一被重训过的那条轴**。

**选择器（`--our` / `--opp`）**：
- `first`：取菜单里官方 score 最高的那个 = **ExampleAI 本体**；
- `random`：菜单里均匀乱选；
- `search`：**本轮新增** —— `BundleMCTS` 的候选菜单由外部注入（`candidate_fn`），
  先验用**均匀**（不掺官方 score，避免把"官方排序"再偷回来），叶子值来自**价值网**，
  出口取**访问次数最多**的候选（项目历史已确立"搜索的增益载体是访问平均，不是价值 argmax"）。

## 3. 臂与预注册判据

全部**镜像配对**（每个 seed 两侧各打一局）、同一 seed 集、K=24、C++ 引擎。

| 臂 | 用途 |
|---|---|
| ① `first` vs `first` | **零假设守卫**：两侧同策略 ⇒ 镜像必须恰好 **0.5000** |
| ② `random` vs `first` | **可行性守卫**：这份菜单**内部的官方排序到底有没有信息**？ |
| ③ `search(value=旧价值网)` vs `first` | 基线 |
| ④ `search(value=新价值网)` vs `first` | 主判据的一半 |

- **主判据**：**④ − ③**（同 seed 配对）> 0 ⇒ (a)（注入数据重训价值网）在**对局层面**有正面效果。
  ⚠️ 这是**配对差值**，不是"能不能打赢 ExampleAI"（我们早就 90.6% 打过 ExampleAI）。
- **可行性守卫②的读法**：若 `random vs first` ≈ 0.50 且 SE 很小 ⇒ **菜单内部的排序没有信息**
  ⇒ ③④ 也不可能有差别 ⇒ 应当停下来重想这条轴，而不是继续加搜索算力。
- ⚠️ 不用 rule_v4 当对手：top-24 菜单**不含闪电**，拿它去打会用闪电的 rule_v4
  等于自断一臂（`rv4_lightning_only` 已证闪电值 ~80pp），结果会被"没有闪电"这个约束主导。

## 4. 成本

搜索成本 ≈ 每次裁决 2.30s（256 iters / depth 4 / k=24 实测）。菜单有 24 个候选 ⇒
**几乎每个回合都要搜**（不像 pos-only 那样 97% 回合可跳过），所以必须压 iterations：
以 64 iters / depth 4 起步，先跑 4 局测单局耗时，再决定 ③④ 的规模（目标 128 对 = 256 局）。

## 5. 实现

1. `code/my_ai/az_intent/bundle_mcts.py`：新增构造参数 `candidate_fn=None`
   （签名 `(state, player, k) -> list[tuple[(op_type,arg0,arg1), ...]] | None`）。
   `None` 返回时**回落到原有采样**（保证旧行为逐位不变）。
   在 `_expand` 里 `node.net_value = ...` 之后插分支：用注入菜单建子节点、先验均匀、
   `intent_counts` 填空（对局不需要训练目标）。
2. `code/test_match/heuristic_candidates_match.py`：新增 `search` 模式 +
   `--search-iters` / `--search-depth` / `--c-puct`；价值网沿用 `--ckpt`（三网 ckpt 取 `value`）。
3. ⚠️ **不动**任何现有默认行为；`candidate_fn=None` 时逐位等价。

## 6. 风险

| 风险 | 说明 |
|---|---|
| 菜单内部无信息 | 见守卫②；这是**最可能**的失败模式（k=8 已见 0.4531）|
| 双方都不放闪电 | 对局可能变得拖长/大量平局 ⇒ 报告里要同时给出平均回合数与平局率 |
| 价值网在最难的分布上被评判 | 两侧的塔态都是价值网的 OOD 区（正是注入想补的），这对③更不利 ⇒ 差值方向仍可解释 |
| 搜索成本 | 先测单局耗时再定规模，不要一上来就 256 局 |
