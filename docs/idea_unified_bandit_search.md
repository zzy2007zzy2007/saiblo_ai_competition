# 想法：把「MC 类仲裁」和「位置 rollout」融成一个统一的 bandit 搜索

> 2026-10-21，用户提出。本文档记录原始想法、我的复述与澄清、以及可以先用数据钉死的几个默认值。
> 状态：**设计阶段**，尚未实现。实现落点计划为 `AZAI_SEARCH=unified`。

## 1. 动因

现状是**两阶段**：

1. **MC 类仲裁**（`mc_quiet`）：菜单 = `{闪电?, HOLD, 最优经济类}`，每个类只用**一个代表动作**
   （该类位置图的 argmax）。安静 rollout 到 `mc_horizon` 回合，取终局 HP 差最大者。
2. **位置搜索**（MCTS 或扁平 rollout）：在**被钉住的那个类**内部，给位置排序。

两个阶段都是 rollout，成本相加；而且第 1 步用"argmax 位置"代表整个类 ——
**一个类可能因为它的 argmax 格不好而被误杀**，这是用户想解决的核心缺陷。

## 2. 用户的原始设计（复述）

假设每回合只放**单个动作**：

维护两张表
- `Q[c]`：类 c 的 rollout 分数（初始相等，或给先验）
- `cursor[c]`：类 c 在位置图降序榜上已用掉的位置数

每轮：
1. 按 `Q[c]` 采一个类；
2. 取该类**位置图降序排名第 `cursor[c]+1` 个**位置（首次即 argmax）；
3. 对该 (类, 位置) 做一次 rollout，更新 `Q[c]`，`cursor[c] += 1`；
4. 直到填满候选预算。

**多动作组版**：
- 分数按每个动作类统计；
- "已用过"的键是 `(类1, 类2, 类3)` 三元组；
- 位置先验 = 三个类位置图**相乘**；
- 选类时三个类分别随机。

**用户自己没定的点**：
- 只用一小部分预算做"生成候选"，留大部分预算复评候选；还是全部预算一次性花完？
- 类分数是否三个头共用（用户倾向共用，但不确定）。

## 3. 澄清（我最初描述有误，这里改正）

我一度用"已经在 A 格建了塔，再去 B 格建塔边际收益下降"来举例，**这个例子是错的**：
单动作版里每个候选都是「同一根局面 + 一个 op + rollout」，候选之间独立，不存在 A、B 互相影响。

**更正 1（原"问题 1"撤回）**：我曾建议"用已观测的 rollout 结果重排该类剩余位置"。
这条**依赖了"邻近格子价值相近"的空间平滑假设**，而该假设在本游戏没有依据
（实测建塔位置 top-1 仅 28%、top-16 才 75–85% ⇒ 格子之间差异很大、不是连续函数）。撤回。

残留的真问题换一种说法（不依赖平滑假设）：
**游标顺序完全由位置图先验决定，而先验本身不准（建塔 top-1 = 28%）**，
纯按先验顺序扫描 = 把预算押在一个 28% 命中率的排序上，且过程中没有机制纠正它。
可行的补丁：位置 ε 随机采样；或把预算更多花在**跨类**探索，而非单类内深扫。

**更正 2（噪声那条的逻辑链要补全）**：

```
游标只前进（永不回退） ⇒ 同一候选不会被再采一次 ⇒ 每个候选最终只有 1 个样本
⇒ 决赛 argmax 比的是两个 σ≈110 的单次观测
```

实测数字：单次 rollout σ≈110；真实 top1−top2 均值差**中位 33.4**（p10 仅 7.3）；
两个单次观测之差的噪声 SD ≈ 110·√2 ≈ 156。
⇒ **P(选错) = Φ(−33.4/156) ≈ 42%**，即典型决策上单样本 argmax 有四成概率选错。

"游标不回头"本身不是罪，**它只是导致"每候选 1 个样本"的机制**。
把第一阶段分数并入第二阶段（复评 top-k 到 ≥30 样本，SE≈20）可把选错率降到 ≈5%。

## 4. 可以用现有数据钉死的三项默认值

### ① 必须两阶段，但**不需要"探索:复评"这个比例参数**

两条实测证据方向相反：
- **覆盖率是主瓶颈**：端到端一致率 55.8% 时，把每候选 rollout 从 48 提到 384，
  条件一致率仅 74.9% → 77.8%（**收益递减**）⇒ 广度优先；
- **但决赛圈需要低噪声**：σ≈110、真实分差**中位 33.4** ⇒ top 候选需 **≥30 采样**（SE≈20）。

**（2026-10-21 修正）** 我原先写的 `phase1_ratio ≈ 0.67` 是**冗余参数**。正确的预算结构是：

```
总预算 = candidate_cap × 1         （生成：每个候选恰好 1 次 rollout）
       + reeval_topk × 每候选样本数（复评：加在已生成的 top-k 上，不丢弃第一阶段分数）
```

即：**宽度只由 `candidate_cap` 决定，剩余预算自然落到复评** ⇒ 只需两个参数，不需要比例。

### ② 类 bandit 必须带探索项

纯按 `Q[c]` 采会过早收敛（某类首次碰巧拿到好位置就一直被选）。
亚军用的是 `q + 600·√(log N / n)`，实测有效 ⇒ 建议 `Q[c] + c·√(log N / n_c)`，`c ≈ 1σ`。

### ③ 多动作组：先纠正一个误判，再谈条件先验

**误判更正**：我曾说"类分数三头共用 ⇒ 无法表达降级+建塔"，**这是错的**。
- **现状代码**是 `pinned = [c] * 3`（三个头被钉成**同一个类**）⇒ 确实表达不了混合；
- **用户的方案**是"分数共用、**采样独立**" ⇒ 各头独立从同一分布采样，**能**表达 (降级, 建塔)。
  例如降级/建塔各 1/2、两槽时，混合组概率正好 50%。⇒ 相对现状是严格改进。

**真正残留的限制是"没有条件结构"**：共用一张表 + 独立采样只能学到
"降级整体好 / 建塔整体好"，学不到"**先降级、再建塔**"这种成对依赖。
而实测模板极端不平衡（见下表）⇒ 条件依赖很强。

建议做法（与"表共用"不冲突）：**表共用（保留用户的简洁）+ 采样加条件**
（head1 按 `P(head1 | head0)` 采）。

真实动作组模板（从亚军 8 局日志统计）：

| 模板 | 占 2-op | 占 3-op |
|---|---|---|
| **降级 + 建塔** | **93.0%** | — |
| 降级 + 升级 / 降级 + 闪电 / 降级 + 降级 / 建塔 + 建塔 | 7.0% | — |
| **降级 + 降级 + 建塔** | — | **92.9%** |
| 降级 + 建塔 + 建塔 | — | 7.1% |

而**现状代码 `pinned = [c] * 3` 三个头钉同一个类 ⇒ 结构上无法表达"降级+建塔"**，
也就是无法表达 93% 的 2-op 动作组。我们实测的出招构成（降级 27%、建塔 46%）
其实都是**跨回合**发生的。

| 方案 | 能否表达 降级+建塔 | 候选空间 |
|---|---|---|
| 三头钉同一个类（= 现状代码 `[c]*3`）| ❌ | 小 |
| 三头独立采类 | ✅ | 笛卡尔积爆炸 |
| **共用一张表 + head1/2 按 `P(head_{i+1} | head_i)` 条件采** | ✅ | ~7 种模板 × 位置 |

⇒ 建议采用第三种。顺带：这同时解释了"为什么我们的升级率是 0–1.4% 而 mcts 有 4.8–6.8%"——
多 op 表达受限时，很多组合根本进不了搜索空间。

## 5. 这个想法真正的价值区间：**h 越大 / op 越多，才越需要 bandit**

单动作的合法空间并不大（24 类 × 32–91 格 ≈ **800 条**）。按实测成本换算：

| 配置 | 单次 rollout | 2.45 s 预算内的 rollout 数 | 能"每条都测一遍"吗 |
|---|---|---|---|
| **h=8** | 0.5 ms | ≈ 4,900 | ✅ **能（~700 条，覆盖全部合法单动作）** |
| h=32 | 2 ms | ≈ 1,225 | 能测 800 条，但复评余量小 |
| h=64 | 4 ms | ≈ 610 | ❌ 测不完，必须靠先验/bandit 引导 |

⇒ **结论（2026-10-21 修正）**：
- **单动作 + 小 h（≤8）**：空间小到可以**穷举**，bandit 结构没必要；
  直接"全部测一遍 + 复评 top-k"更简单也更稳。
- **h 较大（≥32）** 或 **要覆盖 2–3 op 组合**（组合空间上万）：必须靠 bandit 引导，本设计的价值才体现。

实现顺序建议：**先做"穷举 + 复评"这条最稳的**（单动作、h=8），bandit 引导留到多 op 版本再启用。

## 6. 计划中的接口与参数

`AZAI_SEARCH=unified` → `UnifiedBanditSearch`：

| 参数 | 默认 | 含义 |
|---|---|---|
| `candidate_cap` | 64（小 h 时可放大到 ~700 做穷举）| 最多生成多少个**不同**候选 |
| `horizon` | **8** | 每次 rollout 推进回合数 |
| `total_rollouts` | 预算自调节（≈39k 回合 ≈ 2.45 s）| 总预算 |
| `reeval_topk` | 8 | 复评候选数 |
| `ucb_c` | 1.0 × σ | 类 bandit 探索系数（**穷举模式下不需要**）|
| `bundle_heads` | 1 | 先单动作；2/3 走模板先验 |

复用现有零件：`net_fn` 一次前向拿 `action_map` + head logits；`my_ai.decoder` 的 masks 保合法；
叶子评估复用 `FlatRolloutGreedy._leaf_values`（批量值网 / 手写价值）。

## 6b. 实现状态（2026-10-21 已落地）

`code/my_ai/az_intent/unified_action_search.py` → `UnifiedActionSearch`，已接入部署桥接
（`AZAI_SEARCH=unified`，参数 `AZAI_UNI_*`）。

**与设计的两处偏差（实测后必须改的）**：

1. **按类别截断候选**。若把全部合法闪电中心都放进来（实测 235 个），会把建塔/升级挤出候选
   ⇒ 增加 `max_lightning`（默认 32，按先验取前 N）。
2. **叶子评估必须批量**。逐条评估时 `encode_observation`(414 µs) + 值网前向(264 µs) 是主要成本，
   会把每回合从 63 µs 抬到 ~500 µs（实测 9,536 回合要 3.5 s）⇒ 改为"先跑 rollout 收集叶子、
   每 64 个一批评估"。空闲机器估计 **≈0.8 s/决策**（298 rollout × (32×63 µs) + 298 叶 × 678 µs）。

**已验证**：`AZAI_SEARCH=unified` 经桥接构造成功并跑出决策。
**未验证**：升级动作的枚举/评估 —— 冒烟局面里我方 0 塔（脚本建的塔被拆了）⇒ 没有升级候选。
需要拿**真实对局中局**（回放某局到第 200 回合）确认升级候选真的进候选集并被 rollout 评估。

## 7. 待验证的问题

1. 统一搜索 vs 现有 flat（`flat/every1`）：同预算下谁强（64 局内部对打）。
2. 两阶段比例 2:1 是否最优（可扫 1:0 / 2:1 / 1:1）。
3. 模板先验是否真的需要（对比"只允许单 op"）。
4. 类别边际分数（一个类跨多个位置取均值）是否比"单代表动作"更稳 —— 这是本设计最核心的假设。
