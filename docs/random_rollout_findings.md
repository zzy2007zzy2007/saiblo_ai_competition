# 随机化 rollout：从"没用"到"有用"的完整链条（2026-10-23）

## 0. 起点：发现 rollout 是确定性的

原来部署配置是"每个候选动作跑 16 次 rollout 取平均"。实测（`code/test_match/` 下的探针）：

| 每候选采样 | 候选分数（前 3）| 耗时 |
|---|---|---|
| 1 | 0.092069, 0.092069, 0.143419 | 177 ms |
| 16 | **逐位相同** | 919 ms |
| 64 | **逐位相同** | 3,548 ms |

**原因**：`FlatRolloutGreedy` 的 rollout 只做 `sim.advance_round()`——**双方都不出招**，
引擎又是确定性的 ⇒ 16 次采样得到的是同一个叶子，`mean()` 等于单个值。

⇒ 部署配置里 **94% 的算力在重复计算同一个数**。

**后果与兑现**：
- 采样数降到 1，同样的时间预算改买**候选广度**（k=24 → 160）；
- 内部 A/B：**k=160/采样1 = 65.6%（21W-11L），血量差 +5.19（CI[+1.3,+9.0]）**，显著胜部署口径；
- k=160 → 320 只有 53.1%（CI 跨 0）⇒ 因为**该局面的候选空间约 266 个**（k=320 实测只生成 266 个，
  且 k=24/160 去重后仍是 24/160，**候选束零重复**）。

## 1. 亚军的随机化是怎么做的（读源码）

`rs::DefenseSimulator::simulate_round(FastRng &rng)`：

```cpp
tower_attack_phase(rng);              // 塔攻击（随机选目标）
move_phase(rng, forced_moves);        // ★ 敌方蚂蚁随机选方向移动
teleport_phase(rng);                  // ★ 随机传送落点 cells[rng.next_int(cell_count)]
manage_ants();
if (!ignore_enemy_spawns) spawn_enemy_ant(rng);   // ★ 敌方随机生成（lure_v4 里关掉了）
update_effects(rng);
```

关键：**随机的是"环境/敌方"**；我方始终按**候选计划**走
（`apply_operations(simulator, plan.ops)`），之后是 `reactive_turn_operations`（规则驱动，不是随机）。

📌 结论：它的随机性 = **对手与环境的不确定性**，不是"自己也乱打"。

## 2. 我们的四档实验（全部 32 局配对，对照都是部署口径或冠军）

| 变体 | 结果 | 血量差 | 95%CI | 判读 |
|---|---|---|---|---|
| 恒定 p=0.5，**双方** | 34.4% | −7.47 | [−12.3, −2.6] | ❌ 显著更差 |
| 衰减 C=.6/k=3，**双方** | 31.2% | −6.88 | [−11.3, −2.4] | ❌ 显著更差 |
| 衰减 C=.6/k=3，**只对手**，采样 8 | **50.0%** | +0.06 | [−5.3, +5.4] | ⚪ 完全中性 |
| 衰减 C=.6/k=3，**只对手**，**采样 32** | **59.4%** | **+3.69** | [−1.0, +8.4] | ✅ 正向（边缘显著）|

### 两个关键结论

1. **"我方参与随机"一定有害**（双方 34.4% / 31.2%）：它破坏了"候选动作的价值"——
   rollout 里我先随机乱来，那这个候选到底好不好就测不出来了。
2. **"只随机对手"是有信号的，但需要足够采样**：8 次 → 32 次把 50.0% 抬到 59.4%（**+9.4pp**）。
   ⇒ 之前"随机性无用"的判断是错的，**是采样不足让噪声淹没了信号**。

### 为什么"粗暴随机"会把局面打坏（诊断）

`diag_random_rollout_ops.py` 在真实中局跑 16 回合 × 3 样本，记录每回合双方金币/塔数变化：

```
r 6: P1 金-90 塔+1     ← 建一座贵的塔
r 7: P1 金+84 塔-1     ← 下一回合就拆掉
r 8: P0 金-20 塔+1  P1 金+50 塔-1
r 9: P0 金+30 塔-1  P1 金+30 塔-1
合计：塔数 0→4（const 模式下 16 回合能变 5~9 座），但 HP 几乎不动（20→21）
```

⇒ 产生的是 **churn（建了拆、拆了建）**：叶子局面被搅成值网没见过的样子，
而 HP 又几乎没变 ⇒ 值网给的分严重失真。这正是 const 版 34.4% 的成因。

## 3. 记忆化（前缀树）——用户论点与实测

**论点**：随机 rollout 要"大 N 才抹得平噪声"，而朴素实现成本 ∝ N×H；
很多样本会共享**前缀**（前几回合什么都没抽到）⇒ 记忆化能省大量重复模拟。

### 单独件成本（实测）

```
clone            31.9 µs
clone + advance  93.4 µs   ⇒ advance ≈ 61.5 µs（局面变复杂会涨到 ~90）
```

### 前缀共享率（32 条轨迹 × 16 回合，建前缀树后的唯一节点数）

| 配置 | 唯一节点/总计 | 可省 | 首个随机动作的中位回合 |
|---|---|---|---|
| const 0.5 双方 | 373/512 | 27% | 0 |
| decay C=.6 k=3 | 294/512 | 43% | 0 |
| **decay C=.3 k=1** | **75/512** | **85%** | 16（多数样本整段没动）|
| first only C=.6 | 32/512 | 94% | — |

### 实现（`rollout_share_prefix=True` / `AZAI_FLAT_SHARE_PREFIX=1`）

- `_decide_actions()`：只**决定**本回合双方做什么（不落子），供树版复用；
- `_tree_rollout_value()`：按 `(父节点, 本回合 ops)` 缓存子状态，命中就跳过 clone+apply+advance；
- 叶子**批量**评估（第一版每样本单独前向，导致树版反而更慢——已修）。

### 实测收益（k=48 候选，H=16，分数与朴素版**逐位一致**）

| 配置 | 采样 8 | 采样 32 |
|---|---|---|
| decay C=.3 k=1（共享 85%）| 省 **15%** | 省 **38%** |
| decay C=.6 k=3（共享 43%）| **慢 18%** | **慢 12%** |

⇒ 记忆化**只在"共享率高 + N 大"时才赚**；共享率低时每节点多付的 clone 反而亏。

## 4. 当前建议的下一步

把三个改进叠起来（`_ab_random_bign_tree.sh`）：

```
只随机对手 + decay(C=0.3, k=1)（轨迹最贴近"静止"、共享 85%）
+ 采样 64（继续加大，抹平噪声）
+ 前缀树记忆化（省 ~40-60%）
vs 当前冠军（静止 + 采样 1）
```
